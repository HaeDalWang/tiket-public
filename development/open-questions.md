## Hermes 훅이 승인 전이면 쓰는 사람에게 알릴 것인가

Hermes 는 세션 훅을 처음 볼 때 한 번 승인을 묻는다. 터미널이 아닌 곳에서 띄우면 묻지 않고 조용히 건너뛰고
(`agent/shell_hooks.py:957`, v0.20.5), Enter 만 치면 기본값 N 이라 다음 세션에 또 묻는다. 승인 전인 훅은 돌지
않으므로 훅이 스스로 알릴 수 없다 — 알린다면 `fetch-ticket` 이다(이미 Hermes·Windows 대신 지표를 보내는 자리).

애매한 이유는 **"이 사람이 Hermes 를 쓰는가"를 가릴 신호가 없다**는 것이다(2026-10-01 확인).
- `~/.hermes` 가 있어도 안 쓸 수 있다 — 유지보수자가 그렇다. 크론·게이트웨이가 폴더를 계속 건드려 시각도 신호가 아니다
- `hermes hooks doctor` 는 기준이 못 된다. 승인 뒤 스크립트가 바뀌면 "issue" 를 내는데, 실제 실행 판정은
  이벤트+명령만 본다(`shell_hooks.py:899-906`). 자동 업데이트마다 멀쩡한 사람에게 경고가 간다.
  기준은 같은 것을 보는 `scripts/hermes_hook.py --status` 다
- 후보 신호: `fetch-ticket` 을 Hermes 가 실행했을 때 `HERMES_SESSION_ID` 가 보이는가. Hermes 가 자식 명령에 넘기는
  코드는 있지만(`tools/environments/local.py:423-468`) 띄운 방식에 따라 빠질 수 있다 — 모른다

가리는 법: Hermes 쓰는 동료 한 명이 Hermes 세션 안에서 `env | grep HERMES_`. 보이면 "Hermes 안에서 돌고 승인
전일 때만" 알리는 한 줄을 `fetch-ticket.{sh,ps1}` 에 넣는다. 안 보이면 접는다.
`HERMES_ACCEPT_HOOKS=1`·`hooks_auto_accept: true` 는 쓰지 않는다 — 그 사람의 다른 훅까지 승인되고, 0020 과 어긋난다.

## Zendesk 요청 한도를 누가 쓰는가

2026-10-07 09:16 KST 에 유지보수자 PC 의 지표 B·C·D 가 `http_429` 한 번으로 하루치가 비었다. 한도는 분당 400 이고 **계정 전체가 나눠 쓴다**
(응답 헤더 `x-rate-limit: 400`). 우리 수집은 하루 한 번 7회쯤이라 혼자서는 못 닿는다 — 오류 결과는 캐시하지 않고, `fetch-ticket` 은 429 면 `Retry-After` 만큼 기다려 두 번 다시 부르게 고쳤다.
누가 썼는지는 Zendesk 관리자 화면의 API 사용 내역이 가른다(관리자는 경영진). 다시 비면 그때 묻는다. 수집기에 실리는 `stage` 로 어느 호출이 막히는지 볼 수 있다.

## `~/.config/msp/` 의 파일을 하나로 합칠 것인가

2026-10-24 유지보수자 제안: `~/.config/tiket/config.yaml` 같은 한 파일로 모으면 찾기 쉽고 권한·보안에도 낫지 않나.
지금은 자격증명 넷(`zendesk.conf`·`itsm`·`credential-broker.conf`·빌링 플랫폼 키)에 상태·캐시 파일(`tiket-usage-sent`·`tiket-freshness`·`tiket-zendesk-metrics.json` 등)이 섞여 있다.
디렉터리 700·파일 600 은 이미 건다(`onboarding.sh`, `skill_setup.py`).

판단이 갈리는 이유 (2026-10-24 조사):
- **작업이 크다.** 읽는 곳이 추적 파일 38개다 — `scripts/` 와 `skills/aws-customer-account-ops/` 의 `.sh`·`.ps1` 짝, `test/` 의 브로커 테스트까지. 옛 경로를 읽는 이행 단계도 있어야 한다.
- **보안이 나아진다는 근거가 약하다(가설).** 한 파일이면 하나 새면 다 샌다. 스크립트가 자주 다시 쓰는 줄(토큰 캐시 등)과 오래 두는 비밀이 한 파일에서 섞여, 쓰다가 남의 줄을 덮을 위험이 생긴다.
- **`msp` 는 tiket 만의 이름이 아니다.** `itsm` 의 `DEV_ITSM_API_TOKEN` 처럼 다른 도구와 같이 쓰는 키가 있다 — 옮기면 그쪽이 깨질 수 있다(누가 더 읽는지는 unknown).

더 싼 대안: 파일은 두고 `onboarding.sh --check` 가 키별 상태를 한 표로 보여 주게 한다(지금 단계별로 흩어져 나온다).
다시 꺼낼 신호: 키가 하나 더 늘 때, 또는 동료가 "어디에 뭘 넣었는지 모르겠다" 고 할 때.

## 교훈 후보에 "규칙이 틀렸다" 를 둘 것인가 · `출처:` 를 공식 문서와 관측 근거로 나눌 것인가

[[2026-10-26-lesson-flow-redesign]] P1(2026-10-26)에서 드러났고 P2 에서 다루려다 넘어갔다.
- 보류된 후보 하나가 active 정책 카드와 충돌했다 — 판례가 아니라 카드 정정 사안인데, 종류(pitfall·policy·playbook·customer·miss)에 "있는 규칙이 틀렸다" 가 없다. 지금은 사전 검토가 손으로 가려 낸다.
- `출처:` 칸에 공식 문서 대신 고객 조회 결과가 들어온다. 사전 검토 2단계("출처 URL 로 한 줄 확인")가 그 경우 막힌다.

둘 다 수집기 계약(2.5절)과 검사기를 같이 바꾼다. 4주 지표(P6, 2026-11-23 무렵) 때 같은 일이 또 보였는지 세어 보고 정한다.
