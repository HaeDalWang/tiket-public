## 2. 확인된 사실

- 빌링 플랫폼 래퍼는 **API 키만** 쓰고 브로커 로그인이 필요 없다 — 환경변수나 `credential-broker.conf` 의
  `BILLING_API_KEY` (`aws-customer-account-ops/billing-api.sh:7-8`). 즉 비용 조회는 AWS 조회와 떼어 낼 수 있다.
- 고객 AWS 조회는 사람별 Slack OAuth 로그인으로 브로커에게 받는다 (`get-sts-token.sh:2-3`).
  읽기 전용은 브로커 서버가 막는다 (`agents/runtime-status.md:14`).
- 스킬은 **한 묶음으로** 설치된다 — 빌링 플랫폼을 쓰려고 설치하면 AWS 조회 스크립트도 같이 들어온다.
  설치에는 `example-org/support-skills` GitHub 조직 접근이 필요하다 (`scripts/onboarding.sh` 5단계).

## 4. 설계

1. **역할은 온보딩에서 한 번 고른다** — `엔지니어` / `비엔지니어`. `~/.config/msp/` 에 저장한다.
   통제 수단이 아니라 **설치 범위와 안내**만 바꾼다. 비엔지니어는 Zendesk 단계를 건너뛰고 빌링 플랫폼 키만 받는다.
2. **에이전트가 역할을 안다** — 세션 시작 훅이 역할을 주입한다. 비엔지니어면 `customer-aws-readonly` 는
   hard-lock 과 같은 절대 정지. 요청이 와도 "이 역할에서는 금지"라고 알리고 멈춘다.
   `agents/capability-catalog.md` 에 역할별 열을 둔다. 이건 두 번째 울타리다 — 첫 번째는 U1 의 브로커.
3. **기록** — `tickets/` 와 로컬 번호(0019)를 그대로 쓴다. `산출물` 에 **`논의`** 를 더한다.
   - 필수: `물어본 것`, `확인한 것`(`[확인]/[추측]/[모름]` + 출처), `교훈 후보`. 근거 등급이 이 사람들에게 주는 핵심이다
   - 면제: 링크, 답변 초안, 발송 전 점검 — 밖으로 나가는 글이 없다
   - **나누는 기준은 역할이 아니라 "나가는 글이 있는가"다.** 고객 메일 초안을 쓰면 지금의 산출물(답변+출처 등)이고
     `## 발송 전 점검` 을 통과해야 한다. 특정 고객 얘기면 역할과 상관없이 고객 규칙이 붙는다
   - `scripts/check_ticket_record.py` 가 `논의` 를 구분한다
4. **비용 수치** — 빌링 플랫폼에서 나온 수치만 쓴다는 규칙은 그대로다. 비엔지니어는 AWS 원시 청구에 닿을 길이 없다.
5. **지표** — 사용 지표에 역할을 싣는다. 비엔지니어가 실제로 쓰는지 볼 수 있어야 한다 (사이트 스키마와 맞춰야 해서 뒤로).

## 6. 버린 선택지

- **역할 표시로 고객 조회를 막는다** — 로컬 설정은 누구나 고친다. 두 번째 울타리로만 쓴다
- **비엔지니어에게 Zendesk API 토큰** — 토큰은 사용자에 묶이지 않아 관리자까지 흉내 내고, 2027-04-30 에 없어진다.
  그리고 이들은 토큰이 없다
- **기록을 `tickets/` 밖 새 폴더에** — gitignore·push 차단·지표가 이미 `tickets/` 에 걸려 있다. 새 폴더는 그걸 다시 만들어야 한다

## 7. 확인 결과와 바뀐 설계 (2026-09-30, 유지보수자 답)

- **U1 — 브로커는 사용자를 분류하지 않는다** (유지보수자 답. 스킬 소유자에게 직접 확인하기 전이라 가설 수준).
  스크립트와 사내 Slack 계정만 있으면 누구든 고객 자격증명에 닿는다는 뜻이다. 비엔지니어 "금지"를 막는 서버 쪽 장치가 없다.
  - 그래서 첫 울타리는 **스크립트를 갖지 않게 하는 것**이다. 비엔지니어는 `aws-customer-account-ops` 를 설치하지 않는다.
    GitHub 팀 권한으로 `example-org/tiket` 읽기만 주고 `example-org/support-skills` 는 주지 않는다.
  - 남는 위험: 스크립트는 비밀이 아니라 엔지니어 PC 에서 복사할 수 있다. 그때 막는 것은 규칙(윗선 지시)과
    세션 훅의 절대 정지뿐이다. 진짜 통제는 브로커의 사용자 분류다 — 스킬 소유자에게 요청한다.
  - 비엔지니어만의 문제가 아니다. 지금도 사내 Slack 계정이 있는 누구나 스크립트만 있으면 브로커에 닿는다(가설).
- **빌링 플랫폼은 스킬 없이 받아야 한다.** 스킬을 설치하면 AWS 조회 스크립트가 같이 오기 때문이다.
  - (a) **권장**: 스킬 소유자에게 비용 전용 설치 모드(`billing-api.sh` 만)를 요청한다. 빌링 플랫폼 클라이언트의 주인이 하나로 남는다(0014 취지)
  - (b) 안 되면 `fetch-ticket` 선례(0003 — 외부 스킬에서 필요한 절차만 뽑아 다시 만들었다)처럼 비용 조회만 하는 얇은
    클라이언트를 tiket 에 둔다. 원본의 목적지 검증과 Bearer 취급을 그대로 옮기고 테스트를 먼저 쓴다
- **U2 — 비엔지니어는 GitHub 조직 접근이 없다 → 전체의 선행 조건.** 조직 관리자가 비엔지니어 팀을 만들고
  `example-org/tiket` 읽기만 준다. 이게 없으면 워크스페이스를 설치할 수 없다.
- **U3 — 빌링 플랫폼 키는 사람별 개인 키다.** 누가 조회했는지 빌링 플랫폼 쪽에 남는다. 추가 조치 없음.
- **U4 — 규칙 카드는 역할과 상관없이 전부 적용한다.** "누구나 알고 써야 한다". 역할별 규칙 분기는 만들지 않는다.

### 바뀐 순서

0. GitHub 비엔지니어 팀(`example-org/tiket` 읽기만) — 조직 관리자
1. 스킬 소유자와 한 번에 이야기: 비용 전용 설치 모드 + 브로커 사용자 분류
2. (별개, 기한 있음) 엔지니어 Zendesk OAuth 전환
3. **`논의` 산출물 — 지금 바로 할 수 있다.** 비엔지니어가 없어도 엔지니어의 번호 없는 기술 논의에 쓸모가 있다
4. 역할 온보딩 + 세션 시작 주입 + 능력 표 — 0·1 이 풀린 뒤
5. 비엔지니어용 짧은 안내서
