## 1. 한 줄 목표

`tiket_usage` · `tiket_candidates` 를 읽어 **"무엇을 고칠지"** 를 보여 주는 탭 하나. **보기만** 한다.

화면의 모든 패널은 백로그의 질문 하나에 답해야 한다. 답하는 질문이 없는 그래프는 넣지 않는다.

## 2. 데이터 — 먼저 알아야 할 세 가지 (확인됨, 2026-09-28)

**① 한 행 = 한 사람이 그날 처음 세션을 연 순간의 스냅샷.** 증가분이 아니다.
`tickets.count`, `checks.problems` 는 보내는 순간 그 PC 의 `tickets/` **전체**를 센 누적값이다.
여러 날 행을 더하면 같은 기록이 날마다 다시 세어진다. → 사람별로 **가장 최근 행**을 쓰고, 변화는 **행 사이의 차이**로 본다.

**② `behind` 는 버전이 아니다.** `git rev-list --count HEAD..@{u}` — origin/main 보다 몇 커밋 뒤인가.
자동 업데이트는 태그로 올라가므로, main 에 릴리스 안 된 커밋이 있으면 최신 릴리스여도 0 이 아니다.
→ 버전 칸에 쓰지 않는다. 버전은 `head`(짧은 커밋 해시)로만 보여 준다 (4절 ②).

**③ 후보 승인율은 기간을 정해야 맞다.** 반려·병합 행은 90일 뒤 지워지고, 승인 행은 남는다(`expires_at` 제거).
전체로 세면 승인율이 시간이 갈수록 부풀려진다. → **`created_at` 이 최근 90일 안인 행만** 분모·분자에 쓴다.

### `tiket_usage` 행 (수집기 `lambda/handler.py`, 해시 `engineer` · 정렬 `sent_at`, TTL `ttl` 400일)

| 경로 | 뜻 |
|---|---|
| `engineer` | 온보딩에서 정한 표시 이름 (자유 문자열) |
| `sent_at` | ISO 8601 UTC. 6시간에 한 번(스로틀, 2026-09-29 까지는 24시간), `--force` 면 더 |
| `payload.schema_version` | 지금 `1`. 필드가 늘 수 있다 — **없는 필드는 빈칸으로 견딘다** (v1.0.0 전 스키마는 실험용) |
| `payload.head` | 그 PC 의 짧은 커밋 해시 |
| `payload.behind` | ② 참조. 문자열 숫자 또는 `unknown` |
| `payload.tickets.count` | 기록 파일 수(누적) |
| `payload.tickets.tier` · `.output` | 등급·산출물별 개수. 값이 없으면 `missing`, 못 알아보면 `unclassified` |
| `payload.tickets.policy_field` | `present` · `empty` · `absent` 개수 |
| `payload.tickets.policy_citations` | 정책 카드 ID 별 인용 수 |
| `payload.checks` | `total` · `passed`(옛 행엔 없음) · `failed` · `pre_schema`(미평가 — 실패 아님) · `problems` |
| `payload.checks.problems` | 검사기 문구(숫자는 `N`) → 개수. 예: "`## 교훈 후보` 가 없다 / 비어 있다" |
| `payload.customers` | 고객 프로필 수·채운 칸 |

## 3. 누가 보나

**`lead` · `admin` 만.** 후보 검토 화면(모든 로그인 사용자)과 다르다.

이유: 숫자뿐이지만 **엔지니어 이름별**이다. 동료의 사용 일수·티켓 수가 모두에게 보이면 도구 개선용 지표가
사람 평가로 읽힌다. 온보딩 고지는 "사람들이 어떻게 쓰는지 알아야 **고칠 수 있어서**" 라고 약속했다.
서버에서 막는다(`requireRole(['admin','lead'])`). 메뉴도 그 역할에만 보인다.

## 4. 패널 — 각 패널이 답하는 질문

| # | 패널 | 답하는 질문 (백로그) | 계산 |
|---|---|---|---|
| ① | 사람별 **사용한 날** — 최근 4주, 날짜 × 사람 점 격자 | 실제로 쓰나 (관찰: 사용 지표) | 사람별 `sent_at` 의 **KST 날짜** 중복 제거. 행이 있다 = 그날 세션을 열었다 (티켓 처리와 같지 않다 — 화면에 그렇게 적는다) |
| ② | 사람별 **최근 `head`** · 마지막 전송일 | 자동 업데이트가 닿았나 (관찰: 첫 자동 업데이트) | 사람별 최신 행. 같은 `head` 끼리 묶어 보여 준다. **"최신 버전" 을 사이트에 적지 않는다** — 5절 |
| ③ | 사람별 **기록 수 변화** | 티켓 기록이 늘고 있나 | 사람별 최신 `tickets.count` 와 7일 전 이하 가장 가까운 행의 차이. 줄면 그대로 보여 준다(지운 것) |
| ④ | **검사 실패 항목** 순위 | 어느 규칙이 가장 자주 막히나 → 무엇을 고칠지 | 사람별 **최신 행만** 골라 `checks.problems` 를 합친다. 옆에 `failed` · `pre_schema` 합. 날짜를 더하지 않는다(2절 ①) |
| ⑤ | 등급 · 산출물 분포, `policy_ids` 채움률 | 분류가 되고 있나, 규칙 카드를 인용하나 | ④ 와 같이 최신 행만 합친다. `missing` 비율을 크게 |
| ⑥ | **교훈 후보** — 주별 받은 수, 최근 90일 승인율, 재관측 상위 | 지식 순환이 도나 (관찰: 교훈 후보) | `tiket_candidates` Scan. 승인율 = 승인 / (승인+반려+병합), **`created_at` 90일 안만** (2절 ③). 결정 전은 분모에서 뺀다 |

맨 위에 한 줄: "마지막 수신 `sent_at` · 보낸 사람 N명 · 행 N개". 데이터가 적을 때 그래프를 과하게 읽지 않게.

## 5. 지켜야 할 원칙 — 사이트가 "사실의 원본" 이 되지 않는다

- **최신 릴리스 태그를 사이트에 적거나 설정하지 않는다.** 적는 순간 다음 릴리스 때 틀린다 (tiket 개발 지도와
  같은 원칙: 릴리스와 화면이 어긋나면 안 된다). 지금은 `head` 만 보여 주고 사람이 대조한다.
  나중에 클라이언트가 자기 태그를 보내면(`payload.release`, 7절) 그걸 그대로 보여 준다 — 그때도 "최신" 판정은 하지 않는다.
- 숫자는 **계산만** 한다. 사이트 DB 에 복사하거나 캐시 테이블을 만들지 않는다. 매 요청 Scan 해도 작다
  (하루 사람 수만큼 행, 400일 TTL).
- 이름 문자열을 사이트 `users` 와 이어 붙이지 않는다. 온보딩 이름은 자유 문자열이라 맞는다는 보장이 없다.

## 추가 1 · 검사 실패를 리더가 읽는 묶음으로 (2026-09-28) — 사이트에 넘길 것

배포된 ④ "검사 실패 항목" 이 검사기 원문(`` `## 발송 전 점검` 에 미통과 항목 N/N 개가 남아 있다 `` 같은)이라
팀장·경영진이 읽기 어렵다. **번역은 tiket 이 한다** — 사이트에 번역표를 두면 검사기 문구가 바뀔 때 조용히 틀린다.

**tiket 쪽 (끝남, `v0.1.2` 부터 동료 데이터에 실린다)**

`payload.checks.categories` 가 새로 온다. 다섯 묶음이 **항상 모두** 온다(0 건 포함).

```json
"categories": {
  "safety":  {"name": "안전장치를 건너뜀",   "why": "근거 없이 확인했다고 적었거나 보내기 전 점검을 끝내지 않았다", "records": 3},
  "routing": {"name": "처리 방향을 안 정함", "why": "…", "records": 0},
  "record":  {"name": "기록이 비어 있음",    "why": "…", "records": 2},
  "lessons": {"name": "배운 걸 안 남김",     "why": "…", "records": 0},
  "format":  {"name": "양식 오류",           "why": "…", "records": 0}
}
```

- `records` 는 **그 묶음에 걸린 기록 수**다. 문제 수가 아니다 — 한 기록이 안전장치에서 두 번 걸려도 1
- `name` · `why` 는 검사기(`check_ticket_record.py` 의 `CATEGORIES`)가 정한 문장 그대로다
- 같이 바뀐 것: `tickets.tier` · `.output` · `.policy_field` 가 **그 칸이 양식에 생긴 뒤 쓴 기록만** 센다.
  전에는 도입 전 기록이 `missing` 으로 들어가 "등급 값 없음 50%" 가 됐다(유지보수자 초기 기록 8건). 필드 모양은 같다

**사이트 쪽**

| | 내용 |
|---|---|
| 합치기 | 사람별 **최신 행만** 골라 묶음별 `records` 를 더한다(2절 ① 과 같다). 이름·이유는 행에서 온 것을 쓴다 — 코드로 번역하지 않는다 |
| 보여 주기 | 위: 묶음 다섯 줄 — "**안전장치를 건너뜀** 3건 / 평가 대상 N건" + `why` 한 줄. `safety` 를 맨 위, 0 건도 보인다(0 이 좋은 소식이다). 분모 = 최신 행들의 `checks.total − checks.pre_schema` |
| 원문 | 지금의 항목 목록은 "자세히" 로 접어 아래에 둔다 — 유지보수자가 무엇을 고칠지 볼 때 쓴다 |
| 섞여 있을 때 | `categories` 가 없는 행(옛 버전 동료)은 묶음 합계에서 빼고, 화면에 "N명은 옛 버전이라 묶음에 안 들어감" 을 적는다. 조용히 0 으로 세지 않는다 |
| 분포 | 바꿀 것 없음. 받은 값이 이미 도입 전 기록을 뺀 값이다. 옛 버전 행은 전처럼 `missing` 이 섞일 수 있다 |

**검증**: 계산 단위 테스트에 — 최신 행만 합치는가 · `categories` 없는 행을 빼고 그 사람 수를 세는가 ·
분모가 `total − pre_schema` 인가 · 이름을 행에서 가져오는가(사이트 코드에 "안전장치" 문자열이 없어야 한다).

## 추가 2 · 지표 schema 2 — 믿을 수 있는 숫자로 (2026-09-28) — 사이트에 넘길 것

tiket `v0.1.3` 부터 `payload.schema_version = 2`. 수집기는 1·2 를 모두 받는다. **계산 방식이 바뀌어서 올렸다** —
같은 칸이라도 1 과 2 는 다른 방식으로 센 값이다. 행을 섞어 합칠 때 버전을 본다.

| 바뀐 것 | 이유 (확인한 사실) |
|---|---|
| 평가 기록(합성고객·`평가:`)을 **모든 숫자에서 뺀다**. 뺀 수는 `tickets.evaluation_excluded` | 유지보수자 PC 18건 중 4건(22%)이 평가 케이스였다. 평가 회차를 늘리면 더 커진다 |
| **`recent`** 가 새로 온다 — `recent["7"]`·`recent["28"]` = 기록의 `날짜:` 가 최근 N일(오늘 포함)인 것만 | 누적값은 옛 기록이 영원히 섞여 이번 주에 고쳐도 숫자가 안 움직인다. `undated` = 날짜가 없거나 미래 |
| `tickets.sent` · `recent[N].sent` = `{recorded, empty}` — `## 실제 발송` 이 채워졌나 | 초안이 실제로 쓰였는지의 가장 가까운 신호. **고친 정도는 재지 않는다** — 지금 그 칸은 메모라 유사도가 0.02~0.16(7건) |
| `release` = 이 PC 의 정식 버전(`v0.1.3` 등) | 버전을 해시 대신 이름으로 |
| `behind` **삭제** | origin/main 기준이라 버전이 아니었다 |

`recent[N]` 모양:

```json
"recent": {
  "undated": 0,
  "7":  {"count": 3,  "tier": {...}, "output": {...}, "sent": {"recorded": 1, "empty": 2},
         "failed": 1, "pre_schema": 0, "categories": {"safety": 1, "routing": 0, "record": 0, "lessons": 0, "format": 0}},
  "28": {...}
}
```

`recent[N].categories` 는 **숫자만**이다(이름·이유는 `checks.categories` 에 있다).

**사이트 쪽**

| | 내용 |
|---|---|
| 기본 보기 | 패널 ③④⑤ 를 **최근 28일** 기준으로 (토글: 7일 / 28일 / 전체 누적). 사람별 최신 행의 `recent[N]` 을 더한다 |
| 사용량 | 패널 ①(사용한 날) 옆에 "최근 7일 처리한 기록 N건" — `recent["7"].count` 합. 사용한 날은 "세션을 연 날" 이고 이게 "일한 양" 이다 |
| 발송 | ⑤ 에 "실제 발송 기록률" = `sent.recorded / count` |
| 버전 | ② 는 `release` 가 있으면 그것, 없으면 `head` |
| 섞여 있을 때 | schema 1 행(옛 버전 동료)은 `recent` 가 없다. 창 보기에서 빼고 "N명은 옛 버전이라 빠짐" 을 적는다. 누적 보기에서도 1 과 2 는 평가 기록 포함 여부가 다르다 — 같은 표시를 한다 |

**검증**: 계산 단위 테스트에 — `recent` 가 없는 행을 창 보기에서 빼고 그 사람 수를 세는가 · 발송 기록률 분모가 `count` 인가 ·
`release` 우선, 없으면 `head` · 7/28/누적 토글이 서로 다른 필드를 읽는가.
