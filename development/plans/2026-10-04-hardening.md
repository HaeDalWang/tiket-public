## 다섯 가지

### 1. 고객 티켓 내용을 외부 AI 서비스로 처리하는 것에 대한 회사 승인 — **유지보수자가 확인**

없으면 받는다. 조율자는 질문 문안을 쓴다. 답을 받으면 `policy/pending-review.md` 에 결정으로 적는다.

### 2. "절대 경계" 를 장치로 — Kiro deny 규칙, Zendesk 읽기 전용

근거 (2026-10-04 공식 문서):
- Kiro: "deny > ask > allow — a deny rule always wins regardless of scope". 규칙은 저장소가 심을 수 없고 PC 마다 설치한다(0030 그대로).
- Zendesk OAuth 범위 `read` = "Gives access to GET endpoints". OAuth 클라이언트는 Zendesk 관리자가 Admin Center 에서 만든다.
  액세스 토큰은 5분~2일, 리프레시 토큰은 기본 30일.

할 것:
- **Kiro**: `kiro_permissions.py` 의 `aws` 쓰기 동사·`s3` 쓰기를 지금의 "묻기" 에서 **deny** 로 올린다. `curl` 의 쓰기 호출과
  AWS 실행 MCP 도구(Claude Code 의 deny 5개와 같은 것)도 deny. 이미 설치된 PC 는 세션 시작 때 규칙을 새 것으로 맞춘다
  ("세션 시작이 PC 쪽 상태를 맞추게 한다" 방향, 2026-10-01). 설치 안 된 PC 는 지금처럼 알린다.
  - 한계를 적어 둔다: glob 은 우회된다(`python -c`, 스크립트, 변수). 벽이 아니라 문턱이다. 벽은 토큰 범위와 브로커다.
  - Windows 는 Kiro 의 폴더 해시를 몰라 규칙을 못 넣는다(0030 의 기존 한계).
- **Zendesk**: OAuth 이전(기한 있는 백로그 항목)을 `read` 범위로 한다. 그러면 "초안만" 이 토큰에서 강제된다.
  막힌 곳: OAuth 클라이언트를 만들 Zendesk 관리자 — 유지보수자가 누구인지 확인.

### 3. 배포 경로 — CI 와 서명된 태그

- **CI**: 푸시마다 검사기와 테스트. 깨끗한 복제본으로 미리 돌려 봤다(2026-10-04):
  `git config core.hooksPath .githooks` 가 먼저 있어야 검사기가 통과하고, `test_aws_customer_skill.py` 는 PC 에 설치된 스킬을
  보는 시험이라 CI 에서 뺀다. 그 밖은 통과. macOS 기본 파이썬 3.9 에서 실행 스크립트는 전부 돌고, 테스트 둘만 `tomllib`(3.11+)이 없어 실패한다.
- **서명**: 릴리스 태그를 SSH 키로 서명하고(`git tag -s`), 업데이트 스크립트가 **지금 설치된 버전의** 서명자 목록으로 새 태그를 검증한다.
  새 태그 안의 목록을 믿지 않으므로, 푸시 권한을 얻은 쪽이 목록을 바꿔도 통하지 않는다. 검증에 실패하면 올리지 않고 알린다.
  - 서명자 파일이 저장소에 생기는 순간부터 강제된다. 그 전 버전의 업데이트 스크립트는 검증 없이 그 버전까지 올라온다 — 그래서 순서 문제가 없다.
  - 유지보수자가 정할 것: 서명에 쓸 키(지금 이 저장소에는 서명 설정이 없다), 키가 암호로 잠겨 있으면 릴리스 때 푸는 방법.
- 브랜치 보호는 요금제 때문에 못 건다. 서명이 그 자리를 일부 메운다.
