- 작성: 2026-10-08 (tiket 밖 대화에서 정리 — 유지보수자 + Kiro)
- 상태 (2026-10-08): **계획으로 채택** — 유지보수자가 루트의 제안서(`PROPOSAL-routing-recall.md`)를 여기로 옮기게 했다. 아직 아무것도 만들지 않았다.
  같은 날 평가 결과로 범위를 고쳤다 — **8절이 1~7절보다 우선한다.** 1~7절은 처음 제안 그대로 둔다.
- 범위: 티켓을 처리할 때 **어떤 정책 카드·pitfall·과거 사례를 봐야 하는지 고르는 단계**
- 고객 정보 없음. 아래 숫자·사례는 전부 이 저장소의 tracked 파일(합성 평가 포함)에서 확인한 것이다.

## 1. 출발점 — 왜 이걸 보나

티켓을 처리할 때 "이 건에 걸리는 규칙·플레이북·사례가 뭔지"를 **기계가 도와 정해 주면** 품질이 크게 오를 것 같다는 아이디어에서 시작했다.
처음 떠올린 방법은 외부 판정 모델(TypeSafe **Jev** — 텍스트 대신 선택지+확률을 돌려주는 API)이었다. 검토 끝에 **모델은 나중이고, 먼저 할 것은 측정**이라는 결론이 났다. 그 과정을 남긴다.

## 3. 검토하고 보류한 것 — 외부 판정 모델 (Jev)

## 4. 제안 — 1 → 4 순서, 앞 단계 숫자가 다음 단계를 정한다

### 1단계 · 정답을 붙인다 (측정의 재료)

- 모든 평가 케이스 헤더에 기계가 읽는 줄을 더한다. 기존 `기대 등급:` 과 같은 모양.
  ```
  - 기대 policy_ids: [POLICY-K8S-001]
  - 오적용 금지: [POLICY-CASE-001]      # 근거로 쓰면 실패인 이웃 카드 (없으면 생략)
  - 기대 pitfalls: []
  ```
- EVAL-002, 010~014 는 체크리스트에 이미 있는 값을 옮기면 된다. EVAL-001, 003~009 는 **새로 정한다** (`[]` 도 정답이다).
- **경계 케이스 2~3건 추가** — 두 카드가 겹치는 문의. 예: Basic 계정 + 비용 문의, EKS 컨트롤 플레인 장애(지원 범위 경계), 접근 오류 + 자격증명.
- 완료 기준: 모든 케이스에 세 줄이 있고, 정답은 유지보수자가 정했다.

### 2단계 · 기준선을 잰다 (지금 상태의 숫자)

- 회차 결과의 `policy_ids` 를 1단계 정답과 대조하는 채점기를 둔다 (`eval_run.py` 의 `summary.json` 옆에 붙이거나 별도 스크립트).
- 지표 세 개:
  - **재현율** — 기대 카드 중 기록에 들어간 비율. 가장 중요하다.
  - **오적용** — `오적용 금지` 카드를 근거로 쓴 회차 수. EVAL-010 이 이 유형이다.
  - **과다 로드** — 기대에 없는 카드 수. 참고용 (토큰 비용).
- 아무것도 강제하지 않은 상태로 케이스당 3회 이상. 결과는 `evals/results/` 에.
- 기준선이 먼저인 이유는 `evals/README.md` 와 같다 — 강제 장치를 먼저 넣으면 비교 대상이 사라진다.
- 완료 기준: 위 세 숫자가 케이스별·전체로 남았다.

### 3단계 · 숫자가 나쁘면, 기계 1차 매칭을 붙인다

- 조건: 2단계 재현율이 목표 미달이거나 오적용이 반복될 때만. (목표치는 2단계를 보고 정한다)
- 방식: 스크립트(또는 hook)가 `_routing.md` 의 `Trigger terms` 로 **후보 카드 목록**을 먼저 뽑아 에이전트에게 준다.
  - **더하기만 한다. 빼지 않는다.** 최종 선택은 지금처럼 에이전트가 의미로 한다.
  - 보안·자격증명·비용·개인정보·고객 소통 카드는 매칭되면 무조건 후보에 넣는다 (`_routing.md` Routing rules 와 같은 선).
  - 잘 헷갈리는 이웃 카드 쌍은 후보에 함께 띄워 차이를 보게 한다 (예: `POLICY-CASE-001` ↔ `POLICY-CASE-002`).
- 왜 모델이 아니라 규칙인가: 기계가 검사할 수 있는 건 기계에 맡기되, 지금 규모에서는 키워드 표로 충분하고, 외부로 나가는 데이터가 없다.
- 완료 기준: 같은 케이스·같은 회차 수로 다시 재서 재현율이 올랐고 오적용이 줄었다. 안 오르면 되돌린다.

### 4단계 · 규모가 커지면, 판정 모델로 1차 매칭을 바꾼다

- 진입 조건 (하나 이상):
  - 카드·pitfall 이 키워드 표로 관리가 안 될 만큼 늘었다 (수백 장 수준)
  - 유사 사례 검색 대상이 수천 건이 됐다
  - 3단계 키워드 매칭의 재현율이 더 오르지 않는다
- 조건: **외부 API 금지.** 로컬 실행 오픈 모델(Laya 류를 우리 정답으로 미세조정) 또는 회사 승인된 계정 안의 모델만.
- 1단계 정답 세트가 그대로 모델의 평가 데이터가 된다. 3단계 키워드 매칭을 이겨야만 바꾼다.
- 한국어 성능은 이 단계에서 직접 잰다.

## 5. 사례(과거 티켓)에 대해

- 장기적으로 가장 커질 부분은 "비슷한 과거 사례" 다. 다만 `tickets/` 는 실제 고객 내용이라 로컬 전용이다.
- 팀이 공유할 수 있는 형태는 비식별 `pitfalls/` 다. 사례가 쌓일수록 **`## 교훈 후보` → `report_lessons.py` → pitfall 승격** 흐름이 선택 품질을 좌우한다.
- 그래서 1단계의 `기대 pitfalls` 는 지금은 대부분 `[]` 라도 칸을 만들어 둔다.

## 6. 열린 질문 (유지보수자가 정할 것)

- 2단계 목표 재현율을 몇으로 둘까 — 숫자를 보고 정한다.
- 3단계를 스크립트로 둘까 hook 으로 둘까 (`development/decisions/0020` 의 hook 범위와 맞출지).
- 경계 케이스 후보 중 어떤 걸 먼저 넣을까.
- 이 제안을 `development/plans/` 로 옮길지, backlog 항목으로만 둘지.

## 7. 하지 않은 것

- 이 문서 외에 저장소의 어떤 파일도 바꾸지 않았다. 커밋하지 않았다.
- 진행 중인 staged 변경(`policy/_routing.md`, `evals/cases/EVAL-010~014` 등)과 겹치지 않도록 새 파일 하나만 루트에 두었다.

## 8. 2026-10-08 고쳐 쓴 범위 — 선택만이 아니라 적용을 잰다

제안을 쓴 날 FTR 카드 평가(`evals/results/2026-10-08-eval-012-014-ftr-cards.md`)에서 나온 것:

- 카드가 있는 조건의 회차는 전부 맞는 카드를 골랐다(`EVAL-012`~`015`). **실패는 고른 뒤에 났다** — `GUIDE-HEALTH-001` 을 로드하고도 3/3 이
  "다른 고객사도 확인해 안내드리겠다" 고 썼고, `POLICY-ESC-001` 을 로드하고도 메모·태그가 0/3 이었다. 고친 것은 라우팅이 아니라 카드 문장이다.
- 그러니 재현율만 재면 100% 가 나오고 안심하게 된다.
- `오적용 금지` 는 `policy_ids` 로 채점할 수 없다. `EVAL-010` 에서 `POLICY-CASE-001` 은 통과한 회차의 `policy_ids` 에도 들어간다(`CASE-002` 가 가리킨다).
- 단서: 케이스가 모두 카드 하나를 정조준한 문의다. 두 카드에 걸친 문의에서 선택이 맞는지는 모른다.

바뀌는 것:

| 단계 | 처음 제안 | 고친 것 |
|---|---|---|
| 1 | 헤더에 `기대 policy_ids`·`오적용 금지`·`기대 pitfalls` | `오적용 금지` 대신 **`회신 금지 문구`** — 답변 초안 블록에 나오면 실패인 말. 예: `EVAL-013` "다른 고객사", `EVAL-014` "GetObject 권한을", `EVAL-015` "분리되어" |
| 2 | 재현율·오적용·과다 로드 | 재현율 · **금지 문구 적중(골랐는데 지키지 않음)** · 과다 로드. 보안·비용 카드는 평균과 따로, 놓침 0 을 목표로 본다 |
| 2 | 지금 기준선 | FTR 카드가 커밋된 뒤에 잰다(카드 26장). 그 전에 재면 바로 낡는다 |
| 3·4 | 숫자가 나쁘면 키워드 매칭, 커지면 판정 모델 | 접어 둔다. 경계 케이스에서 재현율이 떨어질 때만 다시 연다 |
| — | 경계 케이스 2~3건 | 그대로. 첫 번째는 EKS 컨트롤 플레인 장애(`POLICY-K8S-001` 의 경계 표를 아직 재지 않았다) |

할 일의 크기: 채점기 스크립트 하나(`summary.json` 옆, TDD), 케이스 헤더 두 줄씩(16건), 경계 케이스 2~3건.
6절의 열린 질문 중 "스크립트냐 hook 이냐" 는 3단계와 함께 접는다.
