- **백로그**: "다음" — 현장 교훈 흐름 다시 짜기. 대기 표의 "지식 순환 2차"·"교훈 후보의 종류·한 줄 꼴"·"리드가 처리 지침을 직접 적게" 를 여기에 합친다.

## 0. 문제 (2026-10-23 유지보수자)

1. **보내는 쪽 기준이 흐리다** — 교훈은 "규칙·사례가 없어서 최선을 다해도 못 한 경우" 에만 와야 한다.
2. **받는 쪽이 판단하기 어렵다** — 읽고 다시 해석해야 승인·기각이 된다. 승인 뒤에도 카드·사례로 다시 써야 해서 밀린다.
3. **승인하면 본문이 사라진다** — 반영하기 전에 원문을 잃는다.

그리고 이 흐름이 효과가 있는지부터 모른다.

- 효과는 **unknown** 이다. `재관측` 0건은 "판례가 쓸모없다" 와 "판례를 읽고 피해서 적을 일이 없었다" 를 가르지 못한다. 4절의 지표로 가른다.

## 2. 새 흐름

```
티켓 기록 ─(보내기 전 질문)─▶ 후보 ─▶ 테이블 ─(AI 사전 검토)─▶ 검토 묶음 ─(사람: 한 줄 결정)─▶ 파일 반영 ─▶ applied
             │                                                                                  (원문은 여기서 지운다)
             └─ 있는 규칙을 안 지킴 → kind: miss ─▶ 평가 케이스 후보 (승인 대기열에 안 들어간다)
```

### 2.1 보내는 쪽 — 질문 하나를 앞에 둔다

T1~T4 는 그대로 두고, 종류를 고르기 전에 묻는다:

> **"이 기록 시점에 저장소에 이걸 막을 규칙·판례·절차가 이미 있었나?"** — `pitfalls/`·`policy/_routing.md`·라우터가 고른 모듈을 찾아본다.

- 있었다 → `kind: miss`, `막을 규칙: <경로>`. 교훈이 아니라 **지켜지지 않은 규칙**이다.
- 도구·버전·환경 문제 → 후보가 아니다(`- 없음`). 세션 시작 업데이트가 맡는다.
- 없었다 → 지금처럼 pitfall·policy·customer. 여기에 **`제안 위치:`** 를 더한다 — 덧붙일 기존 파일, 또는 새 파일 이름.

장치: `check_ticket_record.py` 가 `miss` 에 `막을 규칙:` 경로가 실제로 있는지 본다. 문구만으로는 안 밟는다(지금 방향 1).

### 2.2 받는 쪽 — AI 가 먼저 읽고, 사람은 한 줄로 정한다

`new` 후보를 묶음으로 AI 가 먼저 검토한다. 후보마다:
- `출처:` URL 을 열어 `한 줄:` 이 맞는지 — 맞음 / 틀림 / 확인 못 함
- 겹치는 기존 자산과 다른 후보
- 제안: 승인(어느 파일에 어떤 문장) / 기각(사유) / 병합(대상) / miss 로 돌림
- 반영할 문장 초안

사람은 제안을 보고 승인·기각만 누른다. 이것이 "리드가 처리 지침을 직접 적게" 의 대안이다 — 리드가 쓰는 대신 AI 가 쓰고 리드가 고친다.

### 2.3 반영 — 후보마다 파일 하나, 반영할 때까지 원문을 지킨다

- 반영 단위는 지금처럼 **후보 하나 = 파일 하나**(유지보수자, 2026-10-26). 사전 검토가 문장 초안을 주므로 다시 쓰는 일이 준다.
- 반영은 묶음으로 한다 — 사전 검토 한 번 = 커밋 하나 = 패치 릴리스 하나.
- 상태에 `applied`(화면: "반영됨")를 더한다: `approved` 는 원문을 **지우지 않고**, 커밋 해시를 적어 `applied` 가 될 때 지운다. 문제 3 이 풀린다.

### 2.4 옛 클라이언트

수집기가 후보에 클라이언트 `head` 를 이미 싣는다. 사전 검토가 "새 기준 이전 버전" 을 표시하고, 그 후보는 2.1 질문을 사전 검토가 대신 묻는다.

### 2.5 계약 — P2·P3 공통 (2026-10-26 확정)

수집기는 지금 모르는 `kind` 를 후보 단위로 거부하고(`unknown kind`), 모르는 칸은 `build_item` 이 버린다(confirmed, `lambda/candidates.py`).
그래서 **P3 가 먼저 배포되고 tiket 패치가 뒤따른다.** `schema_version` 은 1 그대로 — 칸을 더할 뿐이다.

| 기록 (`## 교훈 후보`) | 전송 칸 | 규칙 |
|---|---|---|
| `종류: miss` | `kind: "miss"` | 트리거·한 줄은 다른 종류와 같이 필수. `한 줄:` 은 "무엇을 안 지켜 넘어졌나" |
| `막을 규칙: <경로>` | `rule` | `miss` 에 필수. 저장소 상대 경로 `.md`, `..` 금지, 200자 이하. tiket 검사기는 파일이 실제로 있는지도 본다 |
| `제안 위치: <경로 또는 새 파일 이름>` | `proposed_location` | pitfall·policy·playbook 의 선택 칸, 200자 이하. 빠지면 검사기가 경고만 한다 |

상태 전이 (`decide()` 가 정본):

| 전이 | 조건 | 원문(evidence) | TTL(expires_at) |
|---|---|---|---|
| new → approved | miss 가 아닌 것 | **남긴다** | 지운다(행은 영구) |
| new → rejected / merged | 사유 필수 | 남긴다 | 남긴다 |
| approved → applied | 사유 필수(커밋 해시·파일) | 지운다 | 이미 없음 |
| new → applied | **miss 만** (평가 케이스가 됨, 사유 = 케이스 경로) | 지운다 | 지운다 |

`재관측` 과 `miss` 는 다르다 — `재관측` 은 판례의 상황이 다시 왔다는 것(판례가 쓸모 있는지), `miss` 는 규칙이 있었는데 **넘어졌다**는 것(평가 재료).

## 4. 효과를 재는 법 (P6, 2026-11-23 무렵)

| 지표 | 지금 | 뜻 |
|---|---|---|
| 승인율 (승인 ÷ 결정) | 7/16 | 보내는 기준이 맞는지 |
| 새 후보 → applied 걸린 시간 | 재지 않음 | 밀리는지 |
| `miss` 건수와 그중 평가 케이스가 된 것 | — | 기각되던 것이 쓸모를 찾았는지 |

**그만두는 조건**: 4주 뒤에도 승인율이 절반을 못 넘고 `재관측` 이 0 이면, 자동 후보는 T4(사람이 "남겨" 라고 함)만 남기고 `miss` 만 자동으로 모은다.

## 5. 하지 않는 것

- 후보를 동료 에이전트가 승인 전에 읽기(지식 순환 2차) — `재관측` 0 인 지금은 읽게 할 근거가 없다. 4절 뒤에 다시.
- 판례 검색층 — 판례 수십 건이면 라우팅 표로 찾는다(0026 2절).
- 사전 검토를 사이트 서버에서 LLM 으로 돌리기 — P1·P5 가 로컬에서 되는지 본 뒤.

## 6. 정한 것 (2026-10-26 유지보수자)

1. **`miss` 를 서버로 보낸다** — 평가 케이스 재료. 승인 대기열이 아니라 별도 목록.
2. **사전 검토는 유지보수자 로컬 Claude 세션**에서 한다. 새 인프라 없음.
3. **`approved` 는 반영될 때까지 원문을 지킨다.** 상태 이름은 `applied`("반영됨") — `landed` 는 와닿지 않는다고 했다. 대가: 원문이 더 오래 남는다(TTL 90일은 그대로).
4. **반영은 후보마다 파일 하나** — 주제 파일로 묶지 않는다.
5. **승인됐지만 반영 안 된 1건(빌링 플랫폼 Savings Plan)** 을 P1 묶음에 넣는다.
