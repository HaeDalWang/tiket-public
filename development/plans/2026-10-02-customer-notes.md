## 3. 기준과 양식 (시험 1호까지 반영)

**적는 조건**: "이 고객의 다음 티켓을 다른 엔지니어가 받았을 때, 이걸 모르면 다르게 행동하게 되는가?"

**적지 않는 것**: 이 티켓에만 해당하는 사실(티켓 기록) · 모든 고객에 해당하는 것(pitfall·정책 카드) ·
다른 시스템에 이미 있는 사실(빌링 플랫폼의 담당자·연락처, 계정 목록) · 사람에 대한 평가 · 자격증명·업무와 무관한 개인 사정.
"깐깐하다" 는 적지 않는다 — "회신마다 근거 링크를 요구함 → 첫 회신부터 공식 문서 URL 을 붙인다" 로 적는다(`CLAUDE.md` 의 사람 기록 규칙).

**항목 하나 = 사실 하나**

```text
- 종류: 접근 제약            (접근 제약 / 계약·범위 / 소통 / 환경)
  강도: 주의                (금지 / 주의 / 참고)
  한 줄: AI 에이전트로 AssumeRole 해 조회할 때는 담당자에게 먼저 알리고, 조회를 꼭 필요한 것으로 좁힌다
  관찰: CloudTrail 에 AssumeRole 알람이 걸려 있다. 읽기 전용이어도 1분에 수십 회 조회하는 패턴이 문제가 된다
  출처: 담당 엔지니어 경험 (YYYY-MM-DD)   (고객 발언 / 내부 전달 / 조회 / 계약서 / 담당 엔지니어 경험)
  대상: 고객 전체            (고객 전체 / 특정 계정 / 특정 담당자)
  재확인: 알람 구성이 바뀔 때
```

- `한 줄` 은 행동으로 끝난다. 환경 사실은 행동 문장이 안 되므로 사실 한 줄 + `그래서:` 로 나눈다.
- 확인하지 않은 기억은 `한 줄` 앞에 `[추측]` 을 붙인다 — 티켓 기록의 등급과 같은 말이다.
- 담당자는 항목이 아니라 블록으로 둔다(문의 방식·결정 범위·기술 수준). 이름·연락처는 빌링 플랫폼에 있으면 적지 않는다.
- `강도` 가 읽는 시점을 정한다 — `금지`·`주의` 는 티켓을 열 때, `참고` 는 회신을 쓸 때.
- 처음에 넣었던 종류 `반복`·`약속` 은 시험 1호에서 한 번도 쓰이지 않아 뺐다.

**시험 1호** (2026-10-02): 유지보수자가 구술한 실제 고객 1곳 — 담당자 둘, 항목 9개(접근 제약 3 · 소통 3 · 환경 2 · 계약·범위 1).
위 양식의 블록·`그래서:`·출처 "담당 엔지니어 경험"·`[추측]` 은 전부 이 시험에서 나왔다.

**아직 정하지 않은 것**: 등급 없는 항목의 기본 등급. 평가에서 출처가 "담당 엔지니어 경험" 인 항목이 티켓 기록에 `[확인]` 으로 넘어왔다.

## 4. 쓰게 만드는 법

- **누구나 적고 고친다. 승인 관문은 없다** — 접근 제약도 바로 공유한다(2026-10-01 유지보수자). 잘못 적힌 잠금은 조회를
  한 번 막을 뿐이지만, 승인을 기다리다 빠진 잠금은 사고다. 지우지 않고 새 항목으로 덮는다.
- 담당 엔지니어가 있는 고객과 담당이 뚜렷하지 않은 일반 고객이 있다.
- **사람이 기억해서 적는 구조는 안 된다** — 공지는 잊힌다(유지보수자). 받아 적는 일은 AI 가 한다:
  ① 엔지니어가 티켓 중에 한 말에서 줍는다 ② 고객이 스레드에 쓴 제약에서 줍는다 ③ 티켓 없이 "특이사항: …" 한 문장으로 받는다.
  닫을 때 "이 둘을 남길까요?" 로 묻고 사람은 예/아니오만 답한다.
- 처음 채우기는 캠페인이 아니라 티켓에 얹는다 — 특이사항이 하나도 없는 고객의 티켓을 처음 열 때 한 번만 묻는다.
- 쓰기만 먼저 내보내지 않는다. 읽히는 것을 봐야 적는다.

## 7. ITSM 에 낸 요청 (2026-10-02 제출, 유형: 기능추가)

접수 번호는 받는 대로 여기 적는다. 아래는 제출 직전 문안이다.
**2026-10-02 답: 긍정적으로 검토 중**(유지보수자 전달). 일정은 모른다.

> **제목**: 고객별 특이사항(접근 제약·대응 방식) 기록 및 고객 단위 조회 API
>
> **요청**
> 1. 고객 정보에 특이사항을 여러 건 기록 — 종류(접근 제약/계약·범위/소통/환경), 강도(금지/주의/참고), 내용 한 줄, 근거,
>    확인 여부(확인됨/추측), 재확인 시점(선택), 작성자·작성일(자동)
> 2. 수정·삭제 대신 "무효 처리 + 새 항목" 으로 이력이 남게
> 3. API 로 읽고 쓰기 — 조회는 고객 1곳을 지정해서만, 쓰기는 엔지니어 권한 토큰으로
> 4. 담당이 아닌 고객의 특이사항도 MSP 엔지니어는 조회 가능하게
> 5. 빌링 플랫폼 `corpId` 로 고객을 찾을 수 있게
>
> **꼭 지켜져야 하는 조건**: 전체 고객의 특이사항을 한 번에 내려주는 목록 API 는 만들지 않는다.
>
> **우선순위**: 조회 API 와 `금지`·`주의` 항목이 먼저. 화면은 나중이어도 된다.

**2026-10-02 오후: dev 에 반영됐다 — `SCRUM-893`**(ITSM 개발자 전달). `https://dev.itsm.example.com`, 운영은 반영 전, 화면 없음.
`GET /api/customers/lookup?corpId=` · `GET|POST /api/customers/<id>/notes` · `POST …/notes/<noteId>/invalidate`.

같은 날 dev 토큰(`~/.config/msp/itsm` 의 `DEV_ITSM_API_TOKEN`)으로 불러 봤다. 쓰기는 이름이 시험용인 고객 1곳에만 했고
