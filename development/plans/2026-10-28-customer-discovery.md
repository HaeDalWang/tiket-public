# 고객 발굴 스킬 — 티켓을 기다리지 않고 숨은 니즈·위험·부채·비용 누출을 찾아 먼저 움직인다

- **상태**: 2026-10-28 초안. 착수 전 — 유지보수자 검토 대기.
- **열린 질문**: `open-questions.md` "티켓을 기다리지 않고 고객 히스토리에서 '발굴' 할 것인가" — 이 계획이 확정되면 거기서 지운다.
- **닮은 것**: [[2026-10-26-lesson-flow-redesign]] 의 P1(손으로 먼저 → 쓸 만하면 굳힌다), `scripts/check_ticket_record.py`(관문을 검사기로).

## 0. 목표

엔지니어가 고객 하나를 골라 부르면(미팅 준비·공지 계획) 그 고객의 히스토리·자원·비용에서
**숨은 니즈 · 잠재 위험 · 미뤄진 기술 부채 · 숨은 비용 누출**을 근거와 함께 뽑고, 미팅 안건·공지 초안까지 만든다.
받은 문의에 답하는 데서 끝내지 않고 엔지니어가 먼저 움직이게 돕는 것이 목적이다.

## 1. 정한 것 (2026-10-28 유지보수자)

1. **부를 때만 돈다.** 자동으로 돌리면 토큰만 쓰고 값이 안 나온다.
2. **워크스페이스 안 스킬**로 둔다 — `aws-customer-account-ops` 와 같은 꼴(`skills/` + 에이전트별 폴더, [[0040-the-customer-skill-moves-into-the-workspace]]).
   한 번 돌리는 playbook(일기)으로는 품질이 안 나온다. 단계를 차례로 밟고 단계마다 검증을 통과해야 한다. 워크스페이스 안이라 `CLAUDE.md` 경계가 그대로 걸린다.
3. **계정 조회는 된다** — 읽기 전용 브로커면 티켓 없이 봐도 된다. 잠금·특이사항이 막는 고객만 뺀다.
4. **시범은 유지보수자 담당 고객 한 곳.**

## 2. 확인한 것 (2026-10-28, 모두 읽기만)

### 2.1 전제 — "티켓이 줄어든다" 는 숫자로 아직 안 보인다

Zendesk `search/count`, 월별 생성 건수(건수만, 내용은 보지 않았다). "기계 발신 제외" 는 [[0007-machine-first-then-work-type]] 표본의 제목 패턴 다섯을 뺀 근사치다.

| 기간 | 전체 (월 평균) | 기계 발신 제외 근사 (월 평균) |
|---|---|---|
| 2025-01 ~ 12 | 3,420 | 828 |
| 2026-01 ~ 05 | 1,781 | 732 |
| 2026-06 ~ 08 | 2,401 | 1,605 — 제외 패턴에 안 걸리는 새 발신이 섞인 것으로 보인다(**hypothesis**, 제목 표본으로 확인) |
| 2026-09 ~ 10 | 1,159 | 725 (10월은 28일까지 774) |

- 전체는 절반 아래로 줄었다 — 대부분 기계 발신 쪽이다. 사람 문의 근사치는 2025 대비 2026 상반기 약 -12%, 9~10월은 비슷하다.
- **읽은 것**: "사람 문의가 AI 때문에 줄었다" 는 아직 **unknown** 이다. 이 계정은 CSG 전체 티켓이라 MSP 담당 고객만의 추세가 아니고, 줄어든 것이 "단순 질문" 같은 특정 종류일 수도 있다.
  이 계획의 근거로는 약하지만 막지는 않는다 — 발굴은 티켓 감소와 무관하게 쓸모가 있는지로 판단한다(7절).

### 2.2 티켓 히스토리는 고객 단위로 모으기 어렵다

- 2026년 티켓(기계 발신 제외 근사 9,924건) 중 **7,806건(79%)에 Zendesk 조직이 비어 있다** — `organization:` 으로 고객별 히스토리를 못 모은다.
  요청자 메일 도메인으로 묶거나, ITSM 티켓(고객 ID 가 붙는다, [[2026-10-06-itsm-ticket-read]], 전환 2027-04 예상)을 기다려야 한다.
- 로컬 `tickets/` 기록은 24건(유지보수자 PC)이고 고객 칸이 없다. 히스토리의 주 재료가 되기에는 얇다.

### 2.3 ITSM CMDB 가 자원 캐시 역할을 할 수 있다 — dev 에서는 된다, 운영은 아직

소스 `~/work/itsm` `origin/dev` `7f509cdc`(Kiro 조사, 주요 주장은 조율자가 소스로 다시 확인) + API 호출(건수·칸 이름만).

- **수집**: 계정마다 작업 큐 → 워커. 자원 수집은 dev 에서 **월 1회**(매월 1일, `lib/cmdb-collector/monthly-run.js`, 월간 보고서용). 운영(main)은 아직 매일 10:30.
  대상은 기술지원 등급 ADV·ENT 또는 허용 목록 고객(`lib/cmdb-collector/eligibility.js`). EC2·EBS·VPC·SG·RDS·S3·Lambda·ECS·EKS·ElastiCache·ELB·CloudFront·DynamoDB 등.
- **상세도**: 자원마다 한 행(`configuration_items`). `version`·`aws_state`·`aws_tags`·`configuration`(JSON — RDS `engineVersion`·`publiclyAccessible`·`storageEncrypted`, S3 암호화·공개 차단 등).
  달마다 스냅샷(`ci_monthly_snapshots`)을 남긴다 — 달 사이 변화를 볼 수 있다.
- **실제로 채워진 칸** (dev 담당 고객 한 곳, CI 1,003건 전부 받아 칸 이름만 셌다):
  - 종류: subnet 292 · SG 125 · route-table 94 · VPC 74 · IGW 73 · EIP 61 · ELB 59 · EBS 55 · S3 49 · EC2 31 · ECR·Lambda 15 · 기타(RDS 4, EKS 4, ElastiCache 3 등).
  - `version` 칸은 비어 있고 버전은 `configuration` 안에 있다 — RDS·ElastiCache `engineVersion`, EKS `version`, Lambda `runtime`, EC2 `imageName`·`platformDetails`.
  - 발굴에 바로 쓸 칸: RDS `publiclyAccessible`·`storageEncrypted`·`multiAZ`·`backupRetentionPeriod`·`deletionProtection`·`autoMinorVersionUpgrade`,
    S3 `encryption`·`publicAccessBlock`·`versioning`·`lifecycle`·`logging`, EBS `encrypted`·`volumeType`·`state`(미연결 볼륨), EC2 `launchTime`·`type`.
  - 없는 것: 사용률(CPU 등 지표), 비용, 태그 외 소유자 정보. 미사용·과대 자원 판단은 CMDB 만으로 안 된다 — 빌링 플랫폼 비용과 겹쳐 봐야 한다.
- **신선도**: CI 별 `last_seen_at`, 계정·종류별 수집 상태, `GET /api/customers/:id/cmdb/freshness`.
- **읽는 길**: `cops_` 토큰으로 `GET /api/customers/:id/cis`(페이지 최대 200), `/cis/summary`, `/cmdb/summary`, `/relationships`, `/api/service-map/{business,technical}/:id`.
  엔지니어 역할의 `/api/customers` 는 **담당 고객만** 돌려준다 — "내 고객" 범위가 저절로 잡힌다. 구성 점검(`/cmdb/checks`)은 내부 전용 경로다.
- **실제 데이터** (유지보수자 토큰, 담당 고객별 건수만):
  - dev: 3곳 중 2곳에 CI 5,053 · 1,003건, 계정 12·5개 전부 수집 완료, 마지막 수집 2026-10-21, 주기 monthly.
  - 운영: 5곳 중 4곳은 CI 0건(수집 대상 계정은 있지만 `never`), 1곳 214건.
- **이미 계산하는 것**: 지원 종료 대조(`lib/report-sections/eol-notices.js` + `backend/data/aws-eol-catalog.json`, 2026-09 판, 손으로 월 1회 갱신 — 단독 API 없음),
  구성 점검 `lib/cmdb-rule-checks.js`(SG 민감 포트 등, PASS·WARN). Security Hub 코드는 못 찾았다. 미사용 자원(`cost-optimizer.js`)은 AWS 를 직접 부르고 저장하는지 못 찾았다.

### 2.4 고객 계정 직접 조회는 "탐지 리스크" 가 있다

스킬 `skills/aws-customer-account-ops/SKILL.md` "3중 방어선이 덮지 않는 것":
읽기 전용이어도 **여러 계정을 짧은 시간에 연속 조회하면 고객 SIEM·GuardDuty 에 정찰로 보인다** — 실제로 보안 문의가 온 사례가 있다.
2개 이상 계정이면 `Step 1.5` 다계정 범위 게이트(열거 → 요약 → 의도 → 승인 → `scope-ack`)를 먼저 통과한다. 허용 액션은 `Describe`·`Get`·`List` 등 9개 접두사.

**읽은 것**: 발굴은 성격상 넓게 본다. 그래서 **넓게 보는 것은 ITSM CMDB·빌링 플랫폼(고객 CloudTrail 에 안 남는다)로, 브로커는 가설 하나를 좁게 확인할 때만** 쓴다.

## 3. 단계 — 단계마다 파일을 남기고, 관문은 검사기가 본다

```
0 범위 ─▶ 1 수집 ─▶ 2 신호 ─▶ 3 검증 ─▶ 4 거르기 ─▶ 5 행동 ─▶ 6 기록
(사람)    (스크립트)  (LLM)     (LLM+조회)  (사람+LLM)  (LLM)      (사람)
```

| 단계 | 하는 일 | 남기는 것 | 관문 (통과 못 하면 다음 단계 금지) |
|---|---|---|---|
| 0 범위 | 고객·목적(미팅/공지/점검)·기간을 정한다. 계정 참조 → 특이사항(`customer_notes.py`) → 잠금 | `00-scope.md` | 잠금이면 멈춘다. 특이사항 종료 2 면 멈춘다 |
| 1 수집 | CMDB 요약·CI·신선도, 빌링 플랫폼 비용 추세·할인, 티켓 목록(가능한 만큼) — LLM 없이 스크립트로 | `10-inventory.json` + 출처·수집 시각 | 출처마다 수집 시각. 신선도가 기준(예: 45일)을 넘으면 표시 |
| 2 신호 | 렌즈 넷(니즈·위험·부채·비용)으로 후보 신호를 넓게 뽑는다 | `20-signals.md` | 신호마다 `근거:` 가 1번 파일의 항목을 가리킨다 — 검사기가 대조 |
| 3 검증 | 신호마다 좁게 확인 — 공식 문서(지원 종료일 등), 필요하면 브로커로 한 자원만 | `30-findings.md` | 발견마다 `confirmed`/`hypothesis`/`unknown`. 라벨 없음·근거 없음은 FAIL |
| 4 거르기 | 엔지니어가 "이미 알던 것 / 이미 처리 중 / 새것" 을 표시. 일반론·근거 없는 것 버림. 영향 × 기한 × 확신으로 순서 | `40-shortlist.md` | 사람 표시가 없는 발견은 5단계로 못 간다 |
| 5 행동 | 미팅 안건, 공지 초안(고객에게 나가는 것은 초안만). 약속·견적은 policy 카드 범위 | `50-actions.md` | 금액은 빌링 플랫폼 출처만, 회신 템플릿·카드 규칙 검사 |
| 6 기록 | 실제로 미팅·공지를 했는지, 고객 반응 | `60-outcome.md` | — (7절 지표의 재료) |

- **왜 파일인가**: 다음 단계는 앞 파일만 읽는다. 고객 히스토리 전체를 한 컨텍스트에 넣지 않으므로 토큰이 적고, 끊긴 곳부터 다시 할 수 있다.
- **왜 검사기인가**: 문구로 단계를 적으면 안 물었을 때 건너뛴다(백로그 지금 방향 1). `check_ticket_record.py` 와 같은 꼴로 `check_discovery.py <폴더>` 가 단계별 관문을 본다.
- **수집기는 갈아 끼운다**: 1단계 입력이 CMDB 가 없으면(운영 지금 상태) 브로커 범위 게이트를 밟아 좁게 모은다. CMDB 가 운영에 오면 그쪽으로 바꾼다.

## 5. 경계

- 고객에게 나가는 것은 초안만. 미팅·공지는 엔지니어가 한다.
- 결과물은 로컬 전용 `excavation/`. 추적 파일(이 계획 포함)에는 고객 이름·계정·`corpId` 를 쓰지 않는다.
- 금액은 빌링 플랫폼 정리 금액만. AWS 원본 청구 수치는 쓰지 않는다.
- 브로커 조회는 3단계에서 가설 하나를 좁게, 2계정 이상이면 범위 게이트.

## 6. 하지 않는 것 (첫판)

- 자동·주기 실행. 다만 날짜가 정해진 신호(지원 종료·약정 만료)는 부를 때만 돌면 늦을 수 있다 — P5 에서 스크립트 주기 실행을 다시 본다.
- 여러 고객 한꺼번에(포트폴리오 훑기). 고객 하나씩.
- ITSM 에 기능 요청(지원 종료 API, 구성 점검 공개 등) — P1 에서 실제로 막히는 것만 모아 한 번에 낸다.

## 8. 모르는 것

- dev CMDB `configuration` 의 칸 이름은 한 고객에서 확인했다(2.3). 값이 얼마나 비어 있는지는 시범 고객으로 P1 1단계에서 본다.
- CMDB 가 운영에 언제 오나(운영 담당 고객 4곳 `never`) — ITSM 쪽 일정.
- 고객별 티켓 히스토리를 어떻게 모으나 — Zendesk 조직 79% 공란. 요청자 도메인으로 묶을지, ITSM 티켓 전환을 기다릴지.
