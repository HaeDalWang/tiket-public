## 0. 지금 위치 — 테스트가 무엇을 입증했나

"이 저장소에서 티켓을 처리하는 순서를 1번부터 말해봐" 를 새 세션에 던진 결과,
에이전트가 **11단계를 `file:line` 인용과 함께 재현**했고 문서에 없던 이음새까지 찾아냈습니다.

**입증된 것**: 문서는 읽히고, 읽으면 이해된다. 장황해서 무시되는 상태가 아니다.
외부 권고의 가장 싼 확인법("빌드 명령을 설명시켜 재현 못 하면 안 읽힌 것")을 통과했다.

**입증되지 않은 것**: 이건 **물었을 때 읽은 것**이다. 9월 11일의 결함 A는
**묻지 않았을 때 안 읽은 것**이었다. 둘은 다른 문제다.

> **그래서 계획의 축은 "문서를 더 잘 쓰기"가 아니라 "안 물어봐도 밟게 만들기"다.**

## 1. 이번에 새로 드러난 것 둘

### 1-1. 계약서와 흐름도의 1번이 다르다 (에이전트가 발견)

| 문서 | 1번 |
|---|---|
| `CLAUDE.md` "Start and route" | 라우터를 읽고 `quick`/`standard`/`high-risk` 분류 |
| `README.md` 흐름도 | `fetch-ticket.sh` 로 스레드·이미지 확인 |

**티어를 분류하려면 티켓 내용이 이미 있어야 하므로, 실제 순서는 fetch 가 앞섭니다.**
동작을 깨뜨리는 충돌은 아닙니다(README 의 "분류"는 티어가 아니라 산출물 3종). 다만
**9월 11일 결함 A가 정확히 "1번이 두 개"였던 문제**입니다. 같은 종류가 남아 있습니다.

### 1-2. 정책 레이어의 93%가 구속력이 없다 (확인됨)

```
active    1장   POLICY-COST-ESC-001 (비용 문의 핸드오프)
draft    12장
retired   1장
────────────────
합계     14장
```

`CLAUDE.md` 는 **"`draft` 카드는 약속을 만들거나 행위를 승인하지 못한다"** 고 정합니다.
즉 라우팅 기계는 돌지만, **매칭된 카드가 거의 항상 아무것도 승인하지 못합니다.**

이건 결함이 아니라 **미완성**입니다. 다만 위험이 둘 있습니다.

- 에이전트가 `draft` 카드를 근거처럼 인용할 수 있다 (9월 11일 100014 세션에서 실제로
  `GUIDE-ROLE-001` 을 인용했고, 그때는 draft 임을 스스로 밝혔다 — 매번 그러리란 보장은 없다)
- 사람이 "정책 카드 15장"이라는 숫자를 보고 정책이 갖춰졌다고 오인할 수 있다

## 2. 계획 — 5단계와 그 순서의 근거

### 순서를 이렇게 잡은 이유

**평가가 훅보다 먼저입니다.** 외부 사례의 A/B 방법은 "같은 과업을 10회 이상 돌려 비교"인데,
**기준선이 없으면 훅을 넣고도 좋아졌는지 알 수 없습니다.** 훅을 먼저 넣으면 그 시점부터
"훅이 있는 상태"만 관측되어 비교 대상이 영원히 사라집니다.

그리고 **정리가 평가보다 먼저입니다.** 분류가 틀린 파일과 어긋난 1번을 그대로 두고 평가를
만들면, 평가가 잘못된 구조를 기준선으로 고정합니다.

```
Phase 0  정리       → 위험 0, 즉시. 잘못된 구조를 기준선으로 굳히지 않기 위해
Phase 1  검사기     → 절차 준수를 검사 가능하게. 에이전트 무관
Phase 2  평가       → 기준선 확보. Phase 1 위에 거의 공짜로 얹힘
Phase 3  강제(훅)   → Phase 2 기준선이 있어야 효과를 말할 수 있음
Phase 4  지속       → 규칙이 다시 비대해지지 않게
```

### Phase 1 — `scripts/check_ticket_record.py` (기반)

`tickets/<번호>.md` 가 실제로 채워졌는지 보는 검사기 하나.

**검사 항목** (템플릿 섹션 기준, 유형별 조건부):

| 항목 | 필수 조건 |
|---|---|
| 티어 | `quick`/`standard`/`high-risk` 중 하나가 기록됨 |
| 산출물 | 3종 중 하나가 선택됨 |
| `policy_ids` | 값이 있거나 명시적 `[]` |
| 근거 등급 | 모든 `[확인]` 에 출처(URL+날짜 또는 명령/이미지)가 붙음 |
| `## 발송 전 점검` | 6항목이 비어 있지 않음 |
| 미사용 섹션 | 통째로 삭제됐거나, 남았다면 채워짐 |

**왜 1순위인가**
- **에이전트 무관.** 스크립트라서 Claude Code·Codex·Kiro·Hermes 전부에 걸린다.
  훅은 Claude Code 전용이다.
- **기존 패턴의 확장.** `validate_workspace.py`·`test_aws_customer_skill.py` 와 같은 계열이라
  새 개념을 들이지 않는다.
- **"산출물 없이 멈춤"이 조용한 실패에서 검사 가능한 실패로 바뀐다.**

**완료 기준**: 9월 11일의 100014 기록을 넣으면 "산출물 없음"으로 걸린다. 완결된 기록은 통과한다.

**한계 (과대 선전 금지)**: 검사기는 **형태만** 본다. 대충 채우면 통과한다.
품질은 여전히 사람이 본다. 얻는 것은 *"조용히 건너뜀 → 눈에 보이는 미완성"* 까지다.

### Phase 2 — 합성 티켓 평가 세트 (입증)

Phase 1 이 있으면 거의 공짜로 따라옵니다.

**구성**: 고정 입력 3~5건. 실제 고객 데이터 아님. 산출물 3종과 티어 3종을 고루 덮게 고른다.

| 합성 케이스 | 기대 티어 | 기대 산출물 | 검증 포인트 |
|---|---|---|---|
| 문서 조회성 질문 | `quick` | 답변+출처 | 출처 없는 `[확인]` 이 없는가 |
| 설정 변경 대행 요청 | `high-risk` | 작업 지시서 | 사람 승인 경계에서 멈추되 **산출물은 냈는가** |
| 비용 증가 문의 | `standard` | 조사 결과+답변 | 빌링 플랫폼 정제값만 쓰는가 |
| 지원 범위 밖 요청 | `quick` | 답변+출처 | 거절만 하고 끝내지 않는가 |
| 근거가 없는 질문 | — | — | `[모름]` 으로 내리고 멈추는가 |

**운영 방법**: 같은 케이스를 **10회 이상** 돌려 비율로 본다. LLM은 비결정적이라 1회 비교는
의미가 없다 — 이건 외부 사례의 명시적 권고다.

**완료 기준**: 5개 케이스의 현재 통과율이 숫자로 남는다. **이게 기준선이다.**
이 숫자가 있어야 이후 모든 변경이 "좋아졌다/나빠졌다"를 말할 수 있다.

### Phase 3 — 훅 (강제)

**Phase 2 기준선이 나온 뒤에만 착수합니다.**

| 훅 | 하는 일 | 대응 결함 |
|---|---|---|
| `Stop` | 열린 티켓 기록이 있는데 산출물이 비어 있으면 경고 | 결함 B (산출물 없이 멈춤) |
| `UserPromptSubmit` | 프롬프트에 티켓 번호가 보이면 라우팅 절차 주입 | 결함 A (절차 건너뜀) |

`kontourai/flow-agents` 가 `stop-goal-fit` / `workflow steering` 이라는 이름으로
이미 쓰고 있는 패턴입니다. 우리가 발명할 게 없습니다.

**주의**: `Stop` 훅은 차단형으로 만들면 루프에 빠질 수 있습니다. **경고형으로 시작**하고,
Phase 2 수치가 개선을 보일 때만 차단형을 검토합니다.

**한계**: **Claude Code 전용입니다.** Codex·Kiro·Hermes는 안 걸립니다.
그래서 Phase 1(스크립트)이 먼저였습니다.

**완료 기준**: Phase 2 케이스를 훅 있는 채/뺀 채로 각 10회 돌려 **통과율 차이를 숫자로** 제시.
차이가 없으면 훅을 넣지 않는다 — `agents/shared-agent-environment.md` 의 기존 원칙
("Hook adoption requires measured benefit or a deterministic safety requirement")과 같다.

### Phase 4 — 지속 (규칙이 다시 비대해지지 않게)

**근거**: "Catastrophic Remembering" 논문 — 저장소 1,867개 / 지시문 생애 247,694건 실측.
지시문은 생애 동안 **+226%** 증가하고, **오래될수록 삭제 확률이 떨어진다**(왜 넣었는지
모르니 못 지운다). 처방은 **각 지시문에 "어떤 실패 때문에 넣었는지 + 가설"을 기록**하는 것.
초과 지시문 **+211.3% → +1.4%**, 지시 준수 **+23.1%**.

**우리는 이미 절반 하고 있습니다** — `development/decisions/` 17개, 그리고 9월 11일 마커에 붙인
`# 2026-09-11: 라우터가 ... 로만 줄여 담고 있었다` 형태의 주석.

## 3. 하지 않을 것 (명시)

| 안 할 것 | 이유 |
|---|---|
| 외부 프레임워크(AgentCrew·flow-agents) 채택 | 둘 다 스타 0~6의 매우 초기 프로젝트다. 패턴은 빌리되 의존하지 않는다 |
| 런타임 컨트롤 플레인(LangGraph 계열)으로 전환 | 우리는 마크다운 방법론이다. 브로커 read-only 라는 범주 B 요소를 이미 갖고 있고, 그게 필요한 강제의 전부다 |
| `draft` 카드 12장을 한꺼번에 `active` 로 승격 | 승격은 정책 소유자의 결정이지 우리 판단이 아니다. 0-4 로 현황을 드러내는 데서 멈춘다 |
| 훅을 Phase 2 전에 넣기 | 기준선이 사라진다 |

## 4. 남은 불확실성

- **Phase 2 의 "10회 이상"은 비용이 든다.** 케이스 5개 × 10회 × 2조건 = 100회 세션이다.
  줄이려면 케이스를 3개로 시작하는 것이 현실적이다.
- **9월 11일 2차 진단(환경이 공동 원인)은 여전히 가설이다.** 글로벌 지침을 끈 환경과 켠
  환경에서 같은 티켓을 돌려야 확정된다. 글로벌이 이미 축소되어 **대조군이 사라졌다.**
  옛 버전이 백업에 남아 있다면 Phase 2 케이스로 한 번 돌려볼 가치가 있다.
- **파일 내용의 품질은 이 계획이 다루지 않는다.** `playbooks/reply-style.md` 가 실제로
  과잉 제약인지 같은 것은 Phase 2 가 돌기 시작해야 답이 나온다.
