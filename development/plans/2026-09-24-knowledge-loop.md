## 0. 문제

첫 문은 열렸다. 티켓을 가져와 분류·분석하고 초안·작업서·슬랙 메시지를 낸다. 그런데 그 결과물은
**그 사람, 그 세션에서 끝난다.** 한 사람이 티켓에서 배운 것이 팀 자산(판례·정책·고객 사정)으로
쌓이지 않는다.

지금 자산이 늘어나는 유일한 경로는 **유지보수자가 기억해 두었다가 손으로 쓰는 것**이다. 판례 7건은
전부 유지보수자 계정으로 추가됐다(`git log --diff-filter=A`, 2026-09-03 ~ 09-24).

**목표**: 누가 처리하든 티켓의 교훈이 자동으로 후보로 모이고, 유지보수자가 검증한 것만 전원에게
근거로 배포된다.

```
티켓 기록 ──(추출)──▶ 후보 ──(수집)──▶ DynamoDB ──(검증: 유지보수자)──▶ git 자산 ──(태그 릴리스)──▶ 전원
 tickets/            ## 교훈 후보      자동 전송        승인 사이트            pitfalls/ 등        0025 자동 업데이트
 [있음]               [없음]            [없음]            [없음]                 [있음]              [있음]
```

가운데 셋이 이 계획의 범위다.

### 3.1 자산 4종 — 나누는 기준은 "누가 확정하나"

| 자산 | 묻는 것 | 확정하는 사람 | 후보가 승인되면 |
|---|---|---|---|

| `playbooks/pitfalls/` | 여기서 넘어진 적 있나 | 유지보수자(검증) | 판례 파일 |
| 고객 사정 | 이 고객은 뭐가 다르지 | 유지보수자(1차) | 공유 고객 프로필 (8절) |

후보 종류는 이 넷 중 하나로 정해져야 한다. 판례가 `playbooks/` 밑에 있어서 이 구분이 폴더에서
안 보였다 — **최상위 `pitfalls/` 로 옮긴다** (P0). `playbooks/` 는 유지보수자가 설계하는 작업 방식,
`pitfalls/` 는 현장에서 검증된 판례, `policy/` 는 회사가 정한 것. 폴더 하나에 확정자 하나다.

### 3.3 승인된 고객 사정은 테이블에 둔다

| 후보지 | 판단 |
|---|---|
| git | **아니다.** 전원에게 매일 배포되는 프레임워크에 고객 원문이 실린다. 1,111개 고객의 자주 바뀌는 사실을 태그 릴리스 주기로 돌리는 것도 모양이 안 맞다 |

| 후보 테이블 (`status=approved`, `kind=customer`) | **지금.** `corpId` 로 이미 묶여 있고, 승인 사이트가 같은 테이블을 본다. ITSM 이 오면 여기서 내보낸다 |

**대가**: 1차에는 승인된 고객 사정이 동료 에이전트에게 **닿지 않는다** (읽는 경로가 범위 밖, 1절).

필요한 고객만 읽으므로 "매칭된 것만 읽는다" 라우팅 원칙과 맞는다.

### 3.2 고객 식별자 — `corpId`

지금 `CUST-NNN` 은 **각 workspace 가 로컬에서 발급한다** (`customers/_index.md`). 그래서 내
`CUST-002` 와 동료의 `CUST-002` 는 다른 고객일 수 있다. 팀 단위로 모으려면 공용 ID 가 필요하다.

## 4. 추출 — 매 티켓이 아니라, 넘어진 티켓만

### 4.1 에이전트가 이걸 판단할 수 있나 — 판단

**"새로운가"는 못 한다.** 에이전트는 다른 동료의 티켓도, 쌓인 후보도 못 본다. 새로움을 묻는 기준은
반복 티켓마다 후보를 만들어낸다.

**"넘어졌나"는 할 수 있다.** 기존 판례를 보면 전부 **기록 안에서 관측 가능한 사건**에서 나왔다.
100016 은 귀책 주체가 두 번 정정됐다(`unconfirmed-attribution-told-to-customer`). 100012 는
`savings-plans-inventory-is-in-billing-platform` 의 관측 사례다. 이런 사건은 기록에 흔적이 남으므로
해석이 아니라 확인이다.

그래서 기준은 **"다음 중 하나가 이 티켓에서 실제로 일어났는가"**다:

| # | 트리거 | 기록의 흔적 |
|---|---|---|
| T1 | 처음 판단이 뒤집혔다 (내 가설, 고객 정정, 귀책 변경) | 기록의 날짜별 정정, `[추측]` → 반대 결론 |
| T2 | 공식 문서·통념대로면 틀리거나 **우리 환경(빌링 플랫폼·Payer·권한 구조)에서 통하지 않았다** | `[확인]` 이 문서와 반대, 또는 고객이 문서 경로를 못 쓴다 |
| T3 | **회사 규칙이 필요한 판단**(약속·권한·금액·계약)을 했는데 카드가 없거나 draft 뿐이었다 | 그 판단의 근거가 `[추측]` 으로 남음. `policy_ids: []` 만으로는 아니다 |
| T4 | 사람이 "이건 남겨" 라고 했다 | 대화 |

**어디에도 해당 없으면 `없음` 이 정답이고, 대부분의 티켓이 그래야 한다.**

추가로 — **기존 판례에 해당하는 티켓**은 새 후보를 만들지 않고 `재관측: <판례 파일>` 한 줄만 남긴다.
반복이 많다는 것 자체가 자산이다. "어느 판례가 몇 번 다시 밟혔나"가 쌓이면 판례의 우선순위와
생사가 숫자로 나온다.

### 4.2 어디에 적나

`templates/ticket-intake.md` 끝에 `## 교훈 후보` 섹션. 에이전트는 템플릿을 따르므로 동료가 할 일은
없다. 칸 형식은 구현 때 정하되 최소:

```
- 없음
  또는
- 종류: pitfall | policy | playbook | customer
  트리거: T1~T4
  한 줄: …
  근거: 기록 안의 위치
- 재관측: pitfalls/<file>.md
```

## 5. 수집 — 사용 지표와 같은 길, 다른 문

### 5.1 사용 지표 수집기에 얹으면 안 되는 이유

사용 지표 수집기는 **식별자가 들어오면 거부하도록** 만들었다 (0021 — 서버가 금지 패턴을 다시
검사하고 `422`). 후보는 정반대로 고객 맥락과 `corpId` 가 **들어 있어야** 한다. 한 엔드포인트에
두 정책을 섞으면 어느 한쪽이 무너진다.

→ **엔드포인트와 테이블을 분리**한다. 전송 **시점**은 공유한다.

| | 사용 지표 | 후보 |
|---|---|---|
| 엔드포인트 | `/ingest` | `/candidates` (신규) |
| 테이블 | `tiket_usage` | `tiket_candidates` (신규) |
| 식별자 | 금지 | `corpId` 필수(고객 건일 때) |
| 비밀값(키·토큰·비밀번호) | 금지 | **여전히 금지** — 서버에서 재검사 |
| 언제 | 세션 시작 하루 1회 | 같은 훅에서 함께 |

### 5.2 같은 후보를 매일 다시 보내지 않기

후보 ID = `hash(엔지니어, 티켓 ID, 한 줄)`. 서버는 조건부 put 으로 **있으면 무시**한다. 클라이언트에
보낸 상태를 저장하지 않는다 — 장비를 옮겨도 중복이 안 생긴다. 한 줄을 고치면 새 후보가 된다(의도).

### 5.4 보존 — 3개월

- 모든 후보에 `expires_at` = 생성 + 90일. DynamoDB TTL 이 지운다
- **승인되면** `evidence`(원문 발췌)를 지우고 `expires_at` 을 없앤다 — 결정과 한 줄 요약은
  영구 기록으로 남고 원문만 사라진다. 판례 파일에는 원래 비식별 일반화만 들어간다
- 반려·미검토는 90일 뒤 통째로 사라진다
- TTL 삭제는 즉시가 아니라 만료 후 며칠 안에 일어난다 — 조회 도구는 `expires_at` 이 지난 행을 거른다

## 6. 검증과 배포

1. 유지보수자가 사이트(나중) 또는 조회 스크립트(당장)로 `status=new` 를 본다
2. 승인 → 3.1 표의 목적지로 **에이전트가 git 파일 초안**을 만들고 유지보수자가 커밋.
   단 `kind=customer` 는 git 으로 가지 않고 테이블의 승인 행이 그대로 자산이다 (3.3)
3. 태그 릴리스 → 0025 자동 업데이트로 전원 반영
4. 반려·병합은 `review_note` 와 함께 테이블에 남는다 — 무엇을 거절했는지도 자산이다

사이트가 붙기 전까지는 조회 스크립트 하나(읽기 + status 변경)로 충분하다.
