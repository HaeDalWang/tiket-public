# 0036. 릴리스 태그는 서명하고, 업데이트는 지금 설치된 버전의 서명자 목록으로 검증한다. 푸시마다 CI 가 돈다

- **언제**: 2026-10-04
- **정한 것** (유지보수자 — 자기 평가의 3번, [[2026-10-04-hardening]]):
  - 릴리스 태그를 SSH 키로 서명한다. 서명자 목록은 `scripts/release-signers`(allowed_signers 형식, 이름은 `tiket-release`).
    키는 이 저장소를 만든 GitHub 계정(`maintainer-gh`)의 것이다.
  - 업데이트(`check-freshness.sh`·`.ps1`)는 올리기 전에 새 태그를 검증한다 — **지금 HEAD 에 커밋된** 목록으로. 새 태그 안의 목록이나
    작업 폴더의 파일은 믿지 않는다. 실패하면 올리지 않고 알린다. HEAD 에 목록이 없으면(도입 전 버전) 지금처럼 올린다.
  - `release.py` 는 HEAD 에 목록이 있으면 서명 없이는 태그를 만들지 않는다. 만든 직후 검증하고, 실패하면 태그를 지운다.
  - 푸시·PR·태그마다 GitHub Actions 가 검사기와 테스트를 돌린다(`.github/workflows/check.yml`, 파이썬 3.9 와 3.12).
- **왜**: 태그가 올라가면 동료 PC 가 세션 시작 때 받아서 그 안의 스크립트를 실행한다(0025). 푸시 권한 하나가 뚫리면 전 동료 PC 에서
  코드가 돈다. 브랜치 보호는 요금제 때문에 못 건다. 검사와 테스트는 한 사람의 PC 에서만 돌았다.
- **확인한 것** (2026-10-04): 임시 저장소·임시 키로 일곱 경우를 sh 와 pwsh 양쪽에서 돌렸다 — 목록의 키 → 올라감 / 목록에 없는 키·
  서명 없음·lightweight → 안 올라감 / 목록 없음 → 올라감 / **새 태그가 목록을 공격자 키로 바꿔도 안 올라감** / 다음 릴리스도 올라감.
  검증 줄을 지우거나 "HEAD 의 목록" 을 "새 태그의 목록" 으로 바꾸는 변이를 테스트가 잡는다. 진짜 키로 버리는 복제본에서 서명·검증 통과.
- **한계**:
  - 목록이 처음 들어오는 릴리스까지는 검증이 없다 — 그 전 버전의 업데이트 스크립트가 검증 없이 받는다. 한 번은 믿어야 한다.
  - 서명 키에 암호가 없다. 이 PC 가 뚫리면 서명도 뚫린다. 막는 것은 "GitHub 계정·토큰만 뺏긴 경우" 다.
  - 키를 바꾸려면 옛 키로 서명한 릴리스가 새 목록을 실어야 한다. 옛 키를 잃으면 동료가 손으로 올려야 한다(`git merge <tag>`).
  - 동료 PC 의 git 이 SSH 서명 검증을 못 하면(git 2.34 미만, ssh-keygen 없음) 올라가지 않고 매번 알린다 — 닫힌 쪽으로 실패한다.
  - **unknown**: Windows PowerShell 5.1 에서의 검증. pwsh 7(macOS)로만 돌려 봤다. 목록 파일을 LF 로 직접 쓰게는 해 두었다.
    v0.1.17 다음 릴리스 때 Windows 동료 한 명의 PC 에서 올라가는지 본다.
  - CI 는 PC 에 설치된 스킬을 보는 `test_aws_customer_skill.py` 를 뺀다. `main` 에 직접 푸시하므로 CI 는 막지 못하고 알릴 뿐이다.
