# 0022. 변경 작업 권한은 강제하지 않고 기록한다 (확정)

- **언제**: 2026-09-23
- **정한 것**: 작업 대행 건의 6번(실제 변경) 단계에서 쓰는 **쓰기 권한을
  프레임워크가 하나로 강제하지 않는다.** 대신 그 고객의 권한 획득 방식을
  **customer profile 에 기록**하고, 작업 지시서는 그것을 참조한다. 실제 권한
  획득·반납과 그에 따른 리스크는 **엔지니어가 판단하고 감내한다.**

- **무엇을 미결로 두고 있었나**: `0009` 가 6번 변경 단계의 쓰기 권한 프로필을
  "아직 안 정한 것"으로 남겼다. `aws-customer-account-ops` 브로커는 서버측에서
  read-only 를 강제하므로 변경에 쓸 수 없고, 지시서에는 `$WRITE_PROFILE` 로
  자리만 잡혀 있었다. `open-questions.md` 의 "변경 작업은 어떤 권한으로 하나"가
  같은 미결이었다.

- **왜 하나로 강제하지 않나** — 원칙과 실무의 간극이 크다

  | | |
  |---|---|
  | **FM / policy** | 매건 **권한 요청 → 작업 → 반납.** 이게 원칙이다. |
  | **실무** | 고객사 히스토리마다 다르다. 예전에 받아둔 write 프로필을 계속 쓰기도 하고, 요청부만 언급하고 진행하기도 하고, 매건 요청·반납을 실제로 도는 곳도 있다. |

  매건 요청·반납을 코드로 강제하면 **현장에서 안 지켜지는 규칙**이 하나 더
  생긴다. 지켜지지 않는 강제는 강제가 아니라 우회 대상이다. 이 저장소는
  "같은 티켓이면 같은 답"을 노리지만, **권한 획득 경로는 고객 계약·신뢰
  관계의 산물이라 티켓 내용만으로 결정되지 않는다.** 그래서 여기는 프레임워크가
  값을 고정할 자리가 아니다.

- **정한 경계** — 강제하지 않는 것과 여전히 지키는 것을 나눈다

  강제하지 **않는** 것:
  - 6번에서 쓸 프로필의 출처 (상시 프로필 / 매건 발급 중 무엇인지)
  - 권한 요청·반납을 매건 돌 것인가

  **여전히 지키는** 것 (바뀌지 않는다):
  - 에이전트는 변경을 실행하지 않는다. 6번 `[변경]` 은 사람이 돈다.
  - 고객 계정 조회는 브로커 경유 read-only 다.
  - 쓰기 자격증명을 이 저장소로 복사하지 않는다 (`infra-change-process.md` hard stop).
  - 사람 게이트·되돌릴 근거·검증 단계는 그대로다.

- **어디에 기록하나**: `templates/customer-profile.md` 의 `## 제약사항` 섹션에
  그 고객의 **쓰기 권한 획득 방식**과 **최종 확인일**을 적는다. 작업 지시서
  6번은 이 프로필 값을 참조하되, 없으면 엔지니어가 그 자리에서 판단한다.
  프로필에 값이 없다고 작업이 막히지는 않는다 — 이건 게이트가 아니라 이력이다.

- **버린 선택지**:
  - **매건 요청·반납을 validator 로 강제** — 현장에서 안 지켜지면 우회 대상이
    된다. 지켜지지 않는 강제를 만들지 않는다.
  - **팀 공용 write 역할 하나로 통일** — 고객사마다 계약·접근 모델이 달라
    성립하지 않는다. 통일할 수 있었으면 애초에 미결이 아니었다.
  - **`$WRITE_PROFILE` 자리표시자 유지** — 무엇을 넣어야 하는지 자체가
    미정이라 자리표시자가 오히려 "정해진 값이 있다"는 오해를 준다. 지시서는
    조회용 `$PROFILE` 만 쓰고, 쓰기 권한은 프로필 참조 주석으로 넘긴다.

- **남는 것**: 이건 프레임워크가 리스크를 **없앤** 결정이 아니라, 리스크를
  **엔지니어에게 명시적으로 귀속시킨** 결정이다. `0002` 가 "tickets 로컬은
  마스킹 안 함"의 위험을 수용한 것과 같은 성격이다.

- **연결**: `0009` 의 "아직 안 정한 것"을 이 결정이 닫는다.
