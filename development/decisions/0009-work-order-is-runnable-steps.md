# 0009. 작업 지시서는 실행 가능한 명령 순서다 (확정)

- **언제**: 2026-09-07
- **정한 것**: 작업 대행 건의 산출물 형식을 **번호 매긴 순서 + 한 줄 설명 + 실행할 명령어**
  로 확정한다. 템플릿에 박고 validator 로 고정했다.

- **왜**: 첫 버전은 티켓에서 대상·값·기간을 뽑아 항목으로 나열한 것이었다. 피드백은
  한 문장이었다 — **"저럴 거면 그냥 티켓 보거든"**. 맞는 말이다. 티켓을 재배열한 것은
  작업 지시서가 아니다. 실행자가 티켓으로 돌아가야 한다면 그 문서는 존재 이유가 없다.

- **형식**

  | 단계 | 성격 |
  |---|---|
  | 1. 계정 확인 | 조회 |
  | 2. 이름으로 실제 대상 찾기 | 조회 — 티켓은 서버 이름을 주지 리소스 ID를 주지 않는다 |
  | 3. 확인한 값을 변수에 세팅 | **이 줄만 고치면 아래가 복붙으로 돌아간다** |
  | 4. 현재 상태를 파일로 저장 | 조회 — 되돌릴 근거 |
  | 5. 기존 설정과 충돌 확인 | 조회 |
  | 6. **[변경]** 실제 변경 | 사람이 실행 |
  | 7. 검증 | 조회 |

- **왜 3번(변수 세팅)이 형식의 일부인가**: 첫 시도는 `<ASG1> <ASG2>` 같은 자리표시자를
  썼는데, bash 가 `<` 를 리다이렉션으로 읽어 **9개 블록 중 5개가 문법 오류**였다.
  복붙해서 못 돌리는 순서는 절차 지향 작업자에게 쓸모가 없다. 변수를 한 번 세팅하는
  단계를 넣으니 전 블록이 `bash -n` 을 통과했다.

- **왜 조회로 시작하는가**: 티켓은 `scs-prd-ntk-all` 같은 **서버 이름**을 주고 AWS 는
  리소스 식별자를 요구한다. 그 간극을 사람이 매번 메우고 있었다.

- **명령어는 공식 문서로 확인하고 쓴다**: 기억으로 쓰면 조용히 틀린다. 100009 에서
  실제로 잡힌 함정 — Auto Scaling cron 은 **기본이 UTC** 라 KST 요청에
  `--time-zone "Asia/Seoul"` 이 없으면 9시간 어긋나고, `--start-time`/`--end-time` 은
  `--time-zone` 과 무관하게 **항상 UTC** 다. 모르고 실행하면 새벽에 증설된다.
  변환 결과와 근거 문서 링크·확인 날짜를 지시서에 같이 남긴다.

- **버린 선택지**:
  - **대상/값/기간 항목 나열** — 폐기된 첫 버전. 티켓 재배열이라 실행자가 티켓을 본다.
  - **완성된 스크립트 파일 한 개** — 한 번에 다 돌면 중간 확인 지점이 사라진다.
    조회와 변경 사이에 사람이 판단할 자리가 있어야 한다.

- **고정 방법**: `validate_workspace.py` 가 `templates/ticket-intake.md` 에서
  `## 작업 지시` · `[변경]` · 변수 세팅 문구 · `되돌릴 근거` · 검증 단계 ·
  `[확인]/[추측]/[모름]` 마커를 검사한다. 항목 나열로 되돌아가면 FAIL 한다.

- **6번 변경 단계의 쓰기 권한** (→ `0022` 에서 확정): 프레임워크가 하나로
  강제하지 않는다. 고객별 획득 방식을 customer profile 에 기록하고, 실제 획득·
  반납은 엔지니어가 판단·감내한다. 지시서는 `$WRITE_PROFILE` 자리표시자를 버리고
  조회용 `$PROFILE` 만 쓰며, 쓰기 권한은 프로필 참조 주석으로 넘긴다.
