# 0040. 고객 AWS 조회 스킬의 클라이언트를 워크스페이스로 들이고, 서버만 따로 둔다 — 0014·0015 를 뒤집는다

- **언제**: 2026-10-08
- **정한 것** (유지보수자):
  - `aws-customer-account-ops` 스킬의 **클라이언트**(스킬 본체·설치·갱신)를 이 저장소로 들인다.
  - **서버**(자격 증명 브로커·버전 관리·감사·접근 대장·알람과 그 배포)는 들이지 않는다. 별도 저장소로 남기고 유지보수자가 맡는다 —
    `tiket-usage-collector` 와 같은 꼴이다. 이 저장소는 여전히 인프라 저장소가 아니다(`CLAUDE.md`).
  - 서버의 **최소 버전 강제는 남긴다.** 자격 증명을 다루는 코드의 보안 수정은 전원에게 닿아야 하는데, 이 저장소의 자동 업데이트는
    멈출 수 있다(고친 파일, 다른 브랜치, fetch 실패 — 2026-10-07 에 조용히 멈추는 길을 넷 찾았다).
  - 순서는 **서버 인수인계가 먼저**다. 거기서 막히면 나머지는 하지 않는다. 계획은 [[2026-10-08-skill-moves-into-workspace]].
  - 오늘 착수하지 않는다. 백로그 1순위로 둔다.

- **왜 이 논의가 다시 나왔나**: 스킬 저장소 관리자가 손을 뗀다. 인프라가 본업이 아닌데 맡아 온 일이고, 앞으로는 이 워크스페이스를
  같이 개발하고 싶어 한다. 세 번째 검토다([[0014-do-not-vendor-the-external-skill]], [[0015-onboarding-installs-the-external-skill]]).

- **확인한 사실** (2026-10-08, 스킬 저장소 `origin/main` `37bba40`, `v1.8.3`, 읽기만):
  - 저장소는 세 덩어리다. 스킬 본체(19개 파일 — 자격 증명 스크립트 sh 204KB·ps1 251KB, `SKILL.md` 43KB),
    설치기(sh 1,603줄·ps1 1,105줄 — 에이전트 9종 폴더·`~/.aws/config`·conf·셸 프로필을 건드린다),
    서버(Lambda 5개가 두 계정의 두 스택에 있다, CodeBuild CI, 카나리).
  - 최근 3개월 병합 제외 커밋 826개(작성자 2명). `infra` 117 · `test` 127 · `skills` 104.
  - 자가 갱신은 Slack 토큰 → 버전 API → 서명된 주소 → SHA256 대조다. 최소 버전에 못 미치면 로그인을 막는다. 대상은 `$HOME` 아래 9개 경로다.
  - **0015 가 든 근거 하나가 풀렸다** — 스킬 본체의 12자리 값이 9개에서 0개가 됐다.
  - 풀리지 않은 것: 설치기에 계정 ARN 하나·API 주소·중간 홉 식별자가 있다(그쪽 관리자 문서는 그 식별자를 "회전 가능한 비밀이 아니다,
    단독 노출 위험 없음" 으로 설계했다고 적는다). 스킬 예시 4개 파일에 회사명 꼴이 21군데 있다 — 실제 고객사인지는 안 가렸다.
  - 스킬 폴더만으로는 여전히 동작하지 않는다. conf 와 `csg-login` 마커는 설치기가 만든다.

- **결정을 뒤집은 사실** (유지보수자가 확인해 준 것 — 내가 잰 것이 아니다):
  - **저쪽에 관리자가 없어진다.** 0014 의 "소유권 — 다른 개발자가 활발히 개발 중이다" 가 사라진다. 그대로 두면 아무도 안 고치는 저장소에
    고객 계정 접근이 걸린다.
  - **스킬만 따로 쓰는 사람이 없다.** 다들 지웠고, 앞으로 단독 배포를 없앤다. 워크스페이스 밖에서 쓰는 사람은 유지보수자 한 명이다.
  - 그래서 0014 의 "5번째 사본이 생겨 자가 갱신과 충돌한다" 도 사라진다 — 자가 갱신 자체를 걷어낸다.

- **들이면 풀어야 하는 것** (계획서의 단계가 하나씩 맡는다):
  - 이 저장소 CI 는 ubuntu 하나다. 스킬은 Linux·Windows 테스트와 카나리를 돈다. 450KB 의 `.ps1` 을 Windows 검증 없이 받지 않는다.
  - 릴리스 서명자가 한 명이다. 같이 개발하면 서명자 목록(`scripts/release-signers`)에 넣을지 정한다.
  - 비식별 계약 — 예시의 회사명을 걷어내고, 설치 상수는 검사기 예외로 둘지 서버에서 받을지 정한다. 예외는 좁게 둔다.
  - 워크스페이스 안 스킬은 이 폴더를 연 세션에서만 보인다. `csg-login` 프로필은 PC 전역이라 AWS CLI 는 어디서든 된다 —
    다른 폴더에서 스킬 문서가 필요한 사람(유지보수자)은 자기 PC 에만 링크를 건다.
  - 자격 증명 코드가 들어오면 릴리스 한 번의 무게가 달라진다. `v1.0.0` 을 그 앞에 둘지 뒤에 둘지 정한다.

- **버린 대안**:
  - **전부 합친다(서버까지)** — 이 저장소의 성격이 바뀐다. 브로커와 IAM 배포가 고객 기록을 다루는 저장소로 들어온다.
  - **저장소는 두고 배포·갱신만 맡는다** — 2026-10-08 오전의 첫 권고였다. "저쪽에 관리자가 있다" 와 "단독 사용자가 있다" 가 전제였고 둘 다 아니었다.
    관리자 없는 저장소의 코드를 받아 까는 구조가 된다.
  - **그대로 둔다** — 고칠 사람이 없는 채로 최소 버전 강제만 살아 있다. 서버가 버전을 올리지 않으면 멈추지는 않지만, 고칠 수도 없다.

- **고정 방법**: 지금은 없다. `test_onboarding_parity.py::test_neither_vendors_the_external_skill` 이 아직 `skills/` 를 막고 있다 —
  계획서 2단계에서 그 테스트를 "들인 스킬이 검사를 통과한다" 로 바꾼다. 그때까지 0014·0015 의 동작(온보딩이 받아서 설치)은 그대로다.
