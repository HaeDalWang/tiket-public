# 0026. 티켓 교훈은 후보 테이블로 모이고, 유지보수자가 승인한 것만 자산이 된다

- **언제**: 2026-09-24

- **정한 것**:
  - 티켓 기록에 `## 교훈 후보` 를 두고, 에이전트가 **넘어진 사건(T1~T4)이 있을 때만** 채운다.
    기존 판례에 해당하면 `재관측` 한 줄만 남긴다. 기본값은 `없음`
  - 기존 사용 지표 훅이 함께 보내되, **엔드포인트와 테이블은 분리**한다(`/candidates`,
    `tiket_candidates`). MSP 회사 인터널 계정에 둔다
  - 고객 키는 빌링 플랫폼 `corpId`. 원문 발췌는 3개월 뒤 TTL 로 사라지고, 승인되면 원문만 지운다
  - 승인은 유지보수자. 판례·정책·절차는 git 으로 가서 태그 릴리스로 배포되고, **고객 사정은 테이블에 남는다**
  - 판례를 `playbooks/pitfalls/` 에서 최상위 `pitfalls/` 로 옮긴다 — 확정자가 다르면 폴더도 다르다

- **왜**: 결과물이 그 사람, 그 세션에서 끝나고 팀 자산으로 쌓이지 않는다. 판례 7건이 전부 유지보수자
  손으로 들어왔다. 동료는 README 를 읽지 않으므로 사람이 할 일이 있는 경로는 돌지 않는다.

- **버린 선택지**:
  - **TencentDB-Agent-Memory 를 런타임으로** — 보안이 아니라 적합성 때문이다. 검증 단계가 없이
    자동 추출하고, system prompt 에 섞어 넣어 라우팅과 draft/active 구분을 우회하고, Kiro 를 지원하지
    않는다. 층 구조 발상만 빌린다
  - **"새로운 교훈인가"를 기준으로** — 에이전트는 다른 동료 티켓과 쌓인 후보를 못 봐서 판단할 수 없다.
    반복 티켓마다 후보가 생긴다
  - **사용 지표 엔드포인트에 얹기** — 그쪽은 식별자를 거부하도록 만들었다(0021). 한 문에 두 정책을
    섞으면 한쪽이 무너진다
  - **고객 사정을 git 에** — 전원에게 매일 배포되는 프레임워크에 고객 원문이 실리고, 자주 바뀌는
    고객 사실과 릴리스 주기가 안 맞는다. 최종 목적지는 ITSM 지식베이스
  - **후보를 동료 에이전트가 즉시 `[추측]` 으로 읽기** — 1차에서는 쌓기까지만. 읽는 경로는 2차

- **근거**: `development/plans/2026-09-24-knowledge-loop.md`, 빌링 플랫폼 `GET /api/admin/v1/companies`
  조회(corpId 1,111개 전부 고유), `git log --diff-filter=A -- playbooks/pitfalls/`

- **이 결정이 닫은 미결** (`open-questions.md` "판례를 어디에 어떻게 모을 것인가", 2026-09-24 삭제):
  - 반복의 첫 관측 — 표본에서 100004 와 100003 이 고객도 담당자도 다른데 한 달 안에 같은 건
    (RDS MySQL 8.0 Extended Support 과금)으로 들어왔다
  - 100008 에 "판례 후보" 섹션을 붙여 본 적이 있다 — `## 교훈 후보` 의 전신이다
  - 당시 "사용 패턴이 쌓인 뒤 정한다"고 미뤘고, 이번에 ITSM 통합 전망과 함께 정했다

- **2026-09-28 덧붙임 — 승인자가 넓어졌다.** MSP 사이트의 승인 화면이 `admin`·`lead` 역할에게 결정을 연다
  (유지보수자 결정). 리드급이 팀 리드·경영진·유지보수자 세 명뿐이라 따로 명단을 두지 않았다. "`v1.0.0` 에 팀장·경영진"
  가 앞당겨진 것이다. 결정 규칙(한 번만, 승인하면 원문 삭제, 반려·병합 사유)은 그대로다.
  [[2026-09-28-candidate-review-site]] 진행 기록.

- **2026-09-29 덧붙임 — 동의 표시 없이 기본 켜짐.** 사용 지표와 교훈 후보 모두 conf 의 `TIKET_ENGINEER`
  없이도 보낸다(이름은 `git user.name`). 끄는 것만 본인이 conf 에 `TIKET_TELEMETRY=off`·`TIKET_LESSONS=off`
  로 적는다. 이유: 이름을 적어야 켜지는 방식에서 `git pull` 만 했거나 AI 로 온보딩한 동료(`llms.txt` 가
  대화형 실행을 막는다)가 조용히 빠졌다 — 3명쯤 쓰는데 행이 없었다. 끄면 다들 불편해진다(유지보수자 결정).
  고지는 줄이지 않고 오히려 넓혔다: 온보딩이 `--check` 까지 매번 보여 주고, `llms.txt` 가 AI 에게 그 고지를
  사람에게 그대로 전하라고 한다. 대가: 이름을 정하지 않은 사람은 `git user.name` 으로 실리고, 나중에
  온보딩에서 다른 이름을 고르면 같은 사람이 두 칸으로 갈라진다(2026-09-24 maintainer-gh·유지보수자와 같은 일).
