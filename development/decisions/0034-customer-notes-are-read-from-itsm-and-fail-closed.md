# 0034. 고객 특이사항은 ITSM 에서 읽고, 못 읽으면 멈추고, 쓰기는 사람이 "예" 라고 한 것만 보낸다

- **언제**: 2026-10-02
- **정한 것** (유지보수자):
  - 고객 특이사항의 자리는 ITSM 의 고객별 특이사항 API 다(`SCRUM-893`). 0031 의 조건 — "고객 키로 물으면 그 고객 것만
    돌아오고, 훑어볼 수는 없어야 한다" — 을 채운다. 2026-10-02 dev 에서 확인했다([[2026-10-02-customer-notes]] 7절).
  - **못 읽으면 멈춘다.** 토큰이 없거나 만료됐거나, 고객을 못 찾거나, 서버가 답하지 않으면 그 고객의 계정 조회를 시작하지 않고
    엔지니어에게 알린다. 읽었는데 항목이 없는 것은 멈춤이 아니다.
  - **쓰기는 사람이 "예" 라고 한 항목만 보낸다.** 받아 적는 것은 AI 가 하고, 보내는 것은 사람이 정한다.
- **왜**: 평가에서 본 사고가 "모르는 채로 조회를 시작한 것" 이었다(0031). `금지` 항목이 있는데 못 읽고 진행하면 같은 사고다.
  잘못 멈춘 조회는 한 번 늦어질 뿐이다. 쓰기는 지울 수 없다 — ITSM 은 무효 처리만 받는다. 실명과 내부 메모가 들어가므로
  틀린 항목이 남는 값이 크다.
- **만든 것**: `scripts/customer_notes.py <corpId> [--dev]` — 읽기만 한다. 실패는 전부 종료 코드 2 와 "계정 조회를 시작하지 않는다".
  돌아온 것이 찾던 고객 것인지 corpId 와 고객 id 로 대조한다. `[확인]`·`[추측]` 은 티켓 기록의 등급과 같은 말로 옮긴다.
- **아직 워크플로에 잇지 않았다.** `CLAUDE.md`·라우터·권한 규칙은 그대로다. 운영에 API 가 없어서 지금 이으면 모든 티켓이
  멈춘다(2026-10-02 운영 `lookup` 은 404). 잇는 조건: 운영 반영, 고객 계정 403 과 내용 노출 범위의 답, 동료 토큰 배포.
- **버린 선택지**:
  - 못 읽으면 경고만 하고 진행 — 평소에는 편하지만 토큰이 만료된 날 `금지` 가 조용히 사라진다
  - 고객을 못 찾은 것(404)만 통과 — `billing_corp_id` 가 빈 고객이 많으면 필요해질 수 있다. 운영의 채움 비율을 보고 다시 정한다
  - AI 가 바로 쓰기 — 엔지니어가 게으르다는 문제는 풀지만, 못 지우는 저장소에 추측이 쌓인다
- **다시 볼 때**: 멈춤이 잦아 엔지니어가 우회하기 시작하면. 운영의 `billing_corp_id` 채움 비율이 낮으면.

## 개정 1 (2026-10-21, 유지보수자) — 운영 반영과 경계

- **운영에 나갔다.** `origin/main` 에 `backend/routes/customer-notes.js`(`34438f68`·`9dc037ab`·`f040a24e`). 운영에서 가짜 corpId 로
  `lookup`·`notes` 가 라우트 자신의 404 JSON 을 돌려줬고(없는 경로는 Express HTML 404), 실제 고객 셋에 `customer_notes.py` 가
  종료 코드 0 "특이사항 없음" 으로 끝났다. 고객 상태는 활성·비활성 둘뿐이다(`f040a24e`). corpId 가 UUID 가 아닌 고객도 있었다.
- **경계: ITSM 조회는 고객 계정 접근이 아니다.** 사내 시스템을 엔지니어 본인의 개인 토큰으로 읽는 일이다. 그래서
  `CLAUDE.md` 의 "broker 경유" 와 `customer-access-locks.md` 의 대상이 아니다 — 잠금은 그 고객 **계정** 조회를 막을 뿐,
  그 고객의 특이사항 읽기는 막지 않는다(잠금 이유를 아는 데 오히려 필요하다). 쓰기 규칙은 위 그대로다.
  토큰에 읽기 전용 범위가 없어(2026-10-21 `origin/dev` 에도 없다) 같은 토큰으로 쓰기가 된다 — 막는 것은 우리 권한 규칙과 "예" 다.
- **토큰은 각자 발급한다.** 하나를 나눠 주지 않는다. ITSM 화면(`/api/me/tokens`)에서 만들어 온보딩이 물어
  `~/.config/msp/itsm` 에 0600 으로 넣는다. 사람마다 토큰이 달라야 ITSM 감사 로그에 누가 읽고 썼는지 남는다.
- **남은 잇는 조건**: 온보딩의 토큰 단계, `CLAUDE.md` 한 줄(위 경계), 라우터, 권한 규칙.

## 개정 2 (2026-10-23, 유지보수자) — 토큰을 등록하지 않은 것은 멈춤이 아니다

- **나눴다.** 토큰 파일이나 `ITSM_API_TOKEN` 키가 없으면 `customer_notes.py` 는 종료 코드 **3** 이고, 에이전트는 계정 조회를
  진행하되 기록에 `특이사항 미확인` 을 남기고 온보딩을 안내한다. 등록한 토큰으로 못 읽은 것(401·만료·서버·네트워크·다른 고객 응답·깨진 파일)은
  그대로 종료 코드 2, 멈춤이다.
- **왜**: 계정 조회는 ITSM 이 아니라 각자의 빌링 플랫폼 키와 브로커로 된다. 멈춤은 문서의 규칙일 뿐이라, 지키면 릴리스 첫날
  토큰을 아직 안 넣은 동료 전원이 키가 있는데도 계정을 못 본다. 처음에 버린 "경고만 하고 진행" 의 걱정 — 토큰이 만료된 날 `금지` 가
  조용히 사라진다 — 은 만료가 "토큰 있음 + 401" 이라 여전히 멈추므로 다시 생기지 않는다. 토큰은 기본으로 만료가 없다(개정 전 7절).
- **남는 빈칸**: 온보딩을 안 한 사람은 특이사항 없이 일한다 — 이 개정 전과 같은 상태다. 잠금 목록(`customer-access-locks.md`)은 토큰과 무관하게 막는다.
