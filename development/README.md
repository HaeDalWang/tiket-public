# development — 이 프레임워크를 어떻게 만들고 있고, 다음에 뭘 하는지

**이 폴더는 프레임워크의 일부가 아닙니다.** 티켓 처리에 쓰이지 않고, 배포본(`export_framework_snapshot.py`)에도 안 들어갑니다.
여기 있는 건 "우리가 이걸 왜 이렇게 만들었는지"와 "다음에 무엇을 할지"에 대한 기록입니다.

**팀이 같이 봅니다.** 저장소를 clone 하면 따라옵니다. 개선 아이디어가 있으면 개인 메모에 두지 말고
`backlog.md` 에 한 줄 적으세요. 누가 무엇을 왜 하려는지가 한 곳에 보여야 같은 일을 두 번 안 합니다.

## 왜 필요한가

만들다 보면 잊어버립니다.

- 3주 전에 왜 그렇게 정했는지 기억이 안 남
- 이미 검토하고 버린 방식을 다시 꺼내서 또 검토함
- 급한 것만 쫓다가 원래 목표에서 멀어짐

그래서 **결정을 내릴 때마다 짧게 적어둡니다.** 나중에 "이거 왜 이래?" 소리가 나오면 여기를 봅니다.

## 목표 (북극성)

> 고객사 기술 티켓에 **AI가 조사하고 초안을 쓰고, 사람이 검토해서 보내는** 방식이
> 엔지니어 여러 명의 실제 업무에서 안정적으로 돌아가는 것.

이게 전부입니다. 판단이 갈릴 때는 이 문장에 가까워지는 쪽을 고릅니다.

세부적으로는 세 가지를 만족해야 합니다.

| 조건 | 뜻 |
|---|---|
| **재현성** | 누가 clone해도 같은 규칙·같은 도구·같은 안전장치가 따라온다 |
| **안전성** | AI가 실수해도 고객 데이터 유출·계정 변경·오발송이 구조적으로 막힌다 |
| **실용성** | 신규 엔지니어가 문서 하나 따라서 하루 안에 시작할 수 있다 |

## 지금 단계

**Alpha** — 사람 검수를 전제로 한 내부 평가 단계입니다.
자율 처리를 목표로 하지 않고, 네 에이전트(Claude Code, Codex, Hermes, Kiro)의 능력이 같다고 보장하지도 않습니다.

## 어떻게 쓰나

| 파일 | 언제 |
|---|---|
| `backlog.md` | **할 일.** 하기로 했지만 아직 안 한 것. 지금 방향도 여기 맨 위에 |
| `plans/` | 한 덩어리 작업의 계획서·검토서. 날짜로 시작하는 파일 하나 |
| `decisions/` | 갈림길에서 뭔가 정했을 때. 하나당 파일 하나 |
| `research/` | 실제로 재보고 나온 숫자. 결정의 근거가 되는 실측 |
| `open-questions.md` | 아직 안 정했거나 일부러 미뤄둔 것 |
| `flow.md` | 프레임워크가 하는 일을 단계로. 단계마다 근거 파일만 적고 **상태는 적지 않는다** |

### 길을 잃었을 때 — 개발 지도

```bash
python3 scripts/dev_map.py          # development/map.html 을 만들어 브라우저로 연다
python3 scripts/dev_map.py --print  # 터미널에서 글로만
```

흐름(`flow.md`) · 릴리스(git 태그) · 백로그 · 계획을 한 화면에 보여 줍니다.
단계가 ✅ 인지는 **사람이 아니라 git 태그가 정합니다.** 근거 파일이 어느 `vX.Y.Z` 에 처음 다 들어갔는지를
볼 때마다 계산하므로, 지도와 릴리스는 어긋날 수 없습니다. 그래서 지도 파일은 커밋하지 않습니다.

### 넷이 어떻게 이어지나

```
open-questions.md ──(정해지면)──▶ decisions/NNNN
        │
        └──(하기로 하면)──▶ backlog.md ──(크면)──▶ plans/YYYY-MM-DD-*.md
                                │
                                └──(끝나면)──▶ 목록에서 지운다. 기록은 git log 와 decisions/ 가 한다
```

- **`open-questions` 와 `backlog` 는 다릅니다.** 앞은 "뭘 할지 아직 모른다", 뒤는 "뭘 할지는 안다, 아직 안 했을 뿐".
- **`plans/` 는 끝나도 지우지 않습니다.** 그때 무엇을 근거로 순서를 정했는지가 남아야 합니다.
  상태가 바뀌면 문서 안에 날짜와 함께 덧붙입니다 (`2026-09-21-usage-telemetry.md` 5절처럼).
- 계획서는 **백로그 항목 하나로 담기지 않을 때만** 만듭니다. 한두 줄이면 백로그로 충분합니다.

`research/` 는 **추정이 아니라 측정**만 넣습니다. 방법·표본 수·한계를 같이 적어야
나중에 "이 숫자 믿어도 되나"를 판단할 수 있습니다. 결정이 실측과 어긋나면 실측이 이깁니다 —
실제로 [[0005-classify-before-answering]] 가 그렇게 개정됐습니다.

### 결정을 적는 기준

**전부 적지 않습니다.** 아래에 해당할 때만 적습니다.

- 나중에 "왜 이렇게 했지?" 소리가 나올 만한 것
- 다른 선택지가 실제로 있었던 것
- 되돌리려면 비용이 드는 것

단순 버그 수정, 오타, 문구 다듬기는 안 적습니다. 그건 git log가 이미 합니다.

### 형식

`decisions/NNNN-짧은-제목.md`. 번호는 순서대로, 파일명은 ASCII로 씁니다.
내용은 아래 5줄이면 충분합니다.

```markdown
# NNNN. 제목

- **언제**: 2026-09-04
- **정한 것**: 한 줄로
- **왜**: 어떤 문제가 있었는지
- **버린 선택지**: 뭘 안 하기로 했는지, 왜 아닌지
- **근거**: 커밋 해시나 파일 경로
```

이미 내린 결정을 **바꿀 때는 기존 파일을 지우지 않습니다.** 맨 아래에 날짜와 함께 덧붙입니다.
왜 바꿨는지가 원래 결정만큼 중요합니다.

### 파일명 함정

`.gitignore` 에 자격증명 보호용 `*credential*`, `*.token`, `*secret*.tfvars` 같은 패턴이 있습니다.
파일명에 그 단어가 들어가면 **조용히 추적에서 빠집니다** — 커밋했는데 없는 상태가 됩니다.
실제로 `0003-credentials-...md` 가 이렇게 빠졌고, `0003-auth-...md` 로 바꿔 해결했습니다.

새 결정 파일을 만든 뒤 확인하세요:

```bash
git check-ignore -v development/decisions/<파일명>   # 아무것도 안 나와야 정상
```
