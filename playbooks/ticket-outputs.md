# 티켓 산출물 3종

티켓을 받으면 **무엇을 만들지부터 정한다.** 유형이 아니라 산출물이 절차를 바꾼다.

| 산출물 | 이런 티켓 |
|---|---|
| 작업 지시서 | 작업 대행, 사전 지원 요청 |
| 조사 결과 + 답변 | 장애·트러블슈팅, 비용·청구, 보안 사고 |
| 답변 + 출처 | 자문·문의 |

고객이 자기 환경을 **바꿔 달라는 요청이 하나라도 있으면 작업 지시서**다(어떻게 설정하면 좋은지 묻는 것은 요청이 아니다). 같이 온 질문은 지시서 안에서 답한다.

---

## 1. 작업 지시서

**고객 회신이 주산출물이 아니다.** 회신은 보통 "설정했습니다" 한 줄이고, 정작 필요한 건
**그것만 보고 콘솔이나 CLI에서 끝낼 수 있는 실행 순서**다.

티켓 내용을 항목으로 옮겨 적는 것은 작업 지시서가 아니다. 그럴 거면 티켓을 보는 게 낫다.
**번호 매긴 순서 + 한 줄 설명 + 실행할 명령어**로 쓴다.

### 형식

````markdown
1. 어느 계정인지 확정한다

   ```bash
   aws sts get-caller-identity --profile <프로필> --output table
   ```

2. 이름으로 실제 리소스를 찾는다 (티켓에는 보통 서버 이름만 온다)

   ```bash
   aws autoscaling describe-auto-scaling-groups --profile <프로필> --region <리전> \
     --query "AutoScalingGroups[?contains(AutoScalingGroupName,'<이름조각>')].AutoScalingGroupName" \
     --output table
   ```

3. **[변경]** 실제로 바꾼다 — 사람이 실행

   ```bash
   aws autoscaling put-scheduled-update-group-action ...
   ```
````

### 규칙

- **조회부터 시작한다.** 티켓은 서버 이름을 주지 리소스 ID를 주지 않는다. 이름 → 실제
  대상을 찾는 read-only 명령이 1번이다
- **바꾸기 전에 현재 상태를 파일로 남긴다.** 되돌릴 근거가 없으면 되돌릴 수 없다
- **변경 명령에는 `[변경]` 을 붙인다.** 에이전트는 조회만 실행하고 변경은 사람이 한다
- **마지막은 검증 명령이다.** 적용됐는지 눈으로 확인하고 끝낸다
- 값은 그대로 적는다. "적절히", "기존과 동일하게" 는 실행 시점에 막힌다
- 시간·타임존·단위처럼 **바꿔 적기 쉬운 것은 변환 결과를 같이 적는다**
  (예: cron 은 기본 UTC 다. KST 요청이면 `--time-zone "Asia/Seoul"` 이 없으면 9시간 어긋난다)

### 에이전트가 하는 일

- **요청 분해** — 한 티켓에 요청이 여러 건 섞여 온다. 번호를 붙여 나눈다
- **명령어 초안** — 공식 문서로 옵션을 확인하고 쓴다. 기억으로 쓰지 않는다
- **누락 지적** — 계정 ID·리전처럼 실행 직전에 막힐 정보를 미리 찾는다
- **위험 표시** — 프로덕션·비가역·과금 영향

## 2. 조사 결과 + 답변

장애와 비용이 같이 묶이는 이유는 둘 다 **"왜 이렇게 됐나"를 증명**해야 하기 때문이다.

증명은 결론만으로 성립하지 않는다. **무엇을 보았고 무엇을 보지 않았는지**를 같이 적어야
`원인 없음` 이 *찾아봤는데 없다* 인지 *안 찾아봤다* 인지 구분된다.

### `## 확인한 것` 의 형식

````markdown
**조사 범위** — 대상 / 기간 / 적용한 필터
- 본 것:
- 보지 않은 것:

**사실**
- [확인] … — 출처
- [추측] … — 무엇으로 확정하는가
- [모름] … — 무엇을 확인하면 풀리는가
````

### 규칙

- **조회는 read-only 만.** 실제 값(리소스ID·버전·지표·금액)을 답변에 옮긴다
- **근거마다 `[확인] [추측] [모름]` 을 붙인다.** `[확인]` 은 이번에 실제로 본 것만
- **원인을 못 찾았으면 못 찾았다고 쓴다.** 그럴듯한 추정으로 채우지 않는다
- **요청의 전제가 사실과 다르면 답하기 전에 정정한다.** 틀린 전제 위에 쌓은 조사는
  통째로 버려진다
- **도구가 막히면 우회하지 않고 기록한다.** 막힌 사실과, 그래서 확인하지 못한 범위를 적는다
- **질문이 여러 개면 각각 답한다.** 하나로 묶으면 빠진 질문이 보이지 않는다
- **비용 건은 고객이 이미 화가 났거나 당황한 상태로 온다.** 사실 나열 전에 상황 인지를
  먼저 적는다. 양식은 `reply-templates.md` 04-B 다
- 고객에게 나가는 금액은 **빌링 플랫폼 정제값만**. 원본 AWS 청구 수치 금지

근거를 초안으로 옮길 때의 규칙(가설 승격 금지, `확인되지 않았습니다`)은
`playbooks/evidence-verification.md` 4번에 있다.

## 3. 답변 + 출처

조회할 리소스가 없어서 **지어내기 가장 쉬운 유형**이다. 에이전트가 제일 잘하는 동시에
제일 위험하다. 그럴듯한 서비스명·룰셋명·옵션명이 근거 없이 나온다.

- 사양·지원 범위·EOL·룰셋 이름 같은 주장은 **공식 문서를 이번에 열어서** 확인한다.
  기억은 근거가 아니다
- 출처 URL 과 확인한 날짜를 남긴다
- 확인 못 한 것은 `[추측]` 으로 명시하고 확정 답변에 쓰지 않는다
- 문서에 없으면 "문서에 없다"가 답이다. 채우지 않는다
- **고객에게도 문서 링크를 같이 준다.** 우리 말을 믿으라고 하지 않는다

### 문서끼리 충돌할 때

AWS 문서는 서로 다르게 적혀 있는 경우가 있다. 조용히 한쪽을 고르지 않는다.

1. **충돌한다는 사실을 기록에 남긴다** — 어느 문서가 뭐라고 하는지 둘 다
2. **어느 쪽을 신뢰하는지와 그 이유를 밝힌다** — 보통 레퍼런스 문서가 블로그·백서보다 정본
3. 고객 답변에는 신뢰하는 쪽만 쓰되, 헷갈리기 쉬운 지점이면 주의를 덧붙인다

### 이름이 비슷한 것을 조심한다

**고객이 쓴 표현을 문서 원문과 직접 대조한다.**

## 어디에 적나

`tickets/<번호>.md` 한 파일 안에 적는다. 유형에 따라 쓰는 섹션이 다르다.

| 산출물 | 쓰는 섹션 |
|---|---|
| 작업 지시서 | `## 작업 지시` |
| 조사 결과 + 답변 | `## 확인한 것` → `## 답변 초안` |
| 답변 + 출처 | `## 확인한 것`(출처 포함) → `## 답변 초안` |

안 쓰는 섹션은 지운다. 빈 제목만 남겨두지 않는다.
