# 회신 템플릿

고객에게 나가는 회신은 아래 원문의 유형(00~11) 가운데 하나를 골라 그 양식으로 쓴다.

- **원문**: 팀 「서포트데스크 답변 템플릿」 v1.4 검토안.
- 원문은 발송 전 체크리스트·10 의 양식·끝의 내부 확인 사항을 뺀 채 손대지 않고 옮겼다. 이 저장소에서 쓰는 법은 바로 아래가 정한다 — 원문과 다르면 아래가 이긴다.

## 이 저장소에서 쓰는 법

1. 산출물(`playbooks/ticket-outputs.md`)을 먼저 정하고, 그다음 회신 유형을 고른다. 기록 머리의 `회신 유형:` 에 번호를 적는다
   (예: `01`, `04-B`, `09+11`). 회신이 없으면 비운다.
2. 양식의 `▪` 라벨 블록을 그대로 쓴다. 해당 없는 라벨과 `[대괄호]` 안내문은 지운다.
3. 고객이 따라 할 절차는 **번호 절차**로 `▪` 블록 아래에 붙여도 된다 — 엔지니어가 정리해 안내하는 편이 낫다.
   한 줄에 한 단계, 단계 사이를 띄운다.
   **고객이 실행할 절차는 위험을 줄이는 순서로 쓴다.** 조회·Pilot·검증을 먼저 두고
   해지·삭제·전체 확대는 뒤에 둔다. 순서가 뒤집히면 되돌릴 수 없는 단계를 먼저 밟게 된다.
4. `[이름]` 은 비워 둔다. 보내는 사람이 채운다. 에이전트는 초안만 쓰고, 공개/비공개 설정과 티켓 상태는 사람이 정한다.
5. 무엇을 쓰는지는 아래 `## 무엇을 쓰나` 가 정한다 — 근거 등급, 고객이 다음에 물을 질문 미리 답하기, 쉬운 말.
   원문의 "발송 전 체크리스트" 는 기록의 `## 발송 전 점검` 으로 옮겼다(공개 댓글 설정 항목은 보내는 사람이 보므로 뺐다).
6. **비용(04·05)**: 원문이 공개 요금 기준 참고 금액이나 비용 변화 수치를 허용해도 이 저장소에서는 `CLAUDE.md` 가 이긴다 —
   고객에게 나가는 금액은 빌링 플랫폼 정제값만 쓴다. 원본 AWS 청구 수치는 쓰지 않는다. 팀의
   비용 업무 분장·정보 공개 범위가 확정되면 다시 본다.
7. 팀 운영 기준은 아직 정해지지 않았다. 진행 안내 주기, 무응답 해결 대기 기간, 비용 문의 분담을
   지어내 초안에 넣지 않는다. 11 의 무응답 안내에 들어갈 날짜(`[O월 O일]`)는 비워 두고 보내는 사람이 정한다.
8. **사람에게 물어야 결정되는 것**은 기록의 `## 내부 확인` 에 적는다 — 무엇을, 누구(역할)에게, 왜. 답은 사람이 받아 적는다.
   답이 빈 동안은 확정 답을 쓰지 않고 02(확인 중)·05·07(이관)로 쓴다. 02·05·07 을 쓰면 `## 내부 확인` 이 비어 있으면 안 된다.
9. 고객 회신·다른 부서·AWS 답을 기다리는 동안 티켓 상태는 **보류**로 둔다. 상태는 사람이 바꾼다 — 초안 밑에 한 줄로 알려 준다.
10. **하지 않은 일을 한 것처럼 쓰지 않는다.** "대응을 시작했습니다", "요청해 두었습니다", "바로 진행하고 있으며" 처럼 아무도 안 한 일을 쓰지 않는다.
   02 의 `진행 중인 작업` 은 실제로 하고 있거나 `## 내부 확인` 에 사람이 할 일로 적은 것만 쓰고, 없으면 그 줄을 지운다.
   접근 잠금·ITSM 특이사항·내부 승인 같은 내부 통제는 답변에 이름을 쓰지도, 해제나 결과를 약속하지도 않는다 — "내부 확인 중" 으로 쓴다.
    - The reply does not say a handoff already happened. Template 07's "전달드렸습니다" is the sentence a human sends **after** forwarding. At draft time nothing has been forwarded: write "전달드리겠습니다" and list the recipient in `## 내부 확인`.

## 무엇을 쓰나 — 내용 규칙

### 순서

초안을 쓴 뒤 **`## 발송 전 점검` 을 통과시킨다.** 이 관문은 형식이 아니라 실제로
나갔던 실패에서 뽑은 항목이다.

에이전트마다 문장·순서·길이는 달라도 된다. 질문, 결론, 확실성, 사실, 미확인, 다음 행동은
같아야 한다. 문장 모양이 아니라 의미를 검증한다.

### Language and tone

- Write customer-facing drafts in formal Korean.
- Use `저희` for first-person plural.
- Lead with the answer or current status, then supporting detail.
- Length follows the ticket's complexity and what the customer needs to understand.
- Before asking a clarification question, explain why the missing information blocks the answer.
- Offer choices when possible and state when an undecided answer is acceptable.
- Preserve technical terms, commands, product names, and identifiers exactly.
- **콘솔 화면을 안내할 때는 고객이 실제로 보는 언어의 UI 명칭을 쓴다.** 한국어 콘솔을 쓰는
  고객에게 영문 메뉴 경로를 주면 화면에서 찾지 못한다. 필요하면 `결제 및 비용 관리(Billing
  and Cost Management)` 처럼 병기한다. 여러 단계를 클릭해야 하는 안내는 스크린샷이 텍스트
  경로보다 빠른 경우가 많다.
- **고객이 문의에서 밝힌 제약 안에서 실행 가능한 답을 준다.** 권한·환경·일정 제약을 고객이
  이미 적었는데 그것을 무시한 경로를 안내하면, 답을 준 것이 아니라 왕복을 만든 것이다.
- **고객에게 조치의 중요도를 말할 때 "급합니다·시급합니다·서둘러 진행해 주세요" 로 재촉하지 않는다.** 담당 엔지니어가 할 말로
  맞지 않는다. "권장드립니다", "가장 우선순위가 높습니다", "먼저 진행하시기를 권장드립니다" 처럼 쓴다.
- **길이를 줄이려고 판단 이유나 이해에 필요한 기술 설명을 삭제하지 않는다.** 간단한 질문을
  불필요하게 늘이지 않는 것과, 근거를 덜어내는 것은 다르다.

### 내용 원칙

- 고객의 표면 질문 뒤에 있는 **실제로 해결하려는 문제**를 보고, 회신을 읽은 고객이 바로 물을 질문
  (적용 조건, 실패 가능성, 기존 구성 유지 여부, 비용·중단 위험, 되돌리기, 확인 방법, 오류 시 조치) 중
  해당하는 것을 미리 답한다. 목표는 고객이 추가 왕복 없이 실행하는 것이다. 모든 가능성을 나열하지는 않고, 밝혀지지 않은 사실을 지어내지 않는다.
- 고정된 줄 수나 문단 수를 두지 않는다. 짧게 쓰는 것 자체가 목표는 아니다.
- 여러 절차를 한 문장이나 한 줄에 압축하지 않는다. 번호 절차는 한 줄에 한 단계, 단계 사이를 띄운다.
- **고객이 한 번에 읽히는 쉬운 말로 쓴다.** 일상에서 잘 안 쓰는 한자어·논문투 단어를 쓰지 않는다.
  `층위가 다르다` → `서로 다른 문제다`, `상충한다` → `서로 맞지 않는다`, `범주` → `종류`, `부재` → `없음`, `상이하다` → `다르다`, `기인한다` → `때문이다`.
  AWS 용어와 제품·화면 이름은 그대로 두되, 처음 나올 때 뜻을 한 줄로 풀어 준다.
- 티켓 기록과 초안에는 고객이 이해하는 실제 계정 이름·alias 를 그대로 쓴다 — `tickets/` 는 로컬 전용이다.
- **고객이 직접 확인할 방법을 준다** — 명령어, 화면 경로, 문서 항목. 직접 확인이 어려우면 확인 결과와 근거를 적는다.
- **링크만 보내고 끝내지 않는다.** 링크는 근거이지 답이 아니다.
- **날짜를 일괄 확약하지 않는다.** 완료·안내 일정은 확인됐거나 고객과 합의한 것만 쓴다.

### Separation

- Only a human sends email or posts to Zendesk.

### Evidence and certainty

- Convert internal evidence into concise customer-safe reasoning.
- If the answer is unknown, state what must be checked or ask for the missing information; never drop a `[모름]` item from the reply silently.

### Relationship context

- Use the preferred salutation and response format recorded in the ticket thread or the customer's ITSM notes.
- Do not infer identity from a short name when the alias map is ambiguous.
- Adapt detail level from observed communication behavior, not a personality judgment.

Style precedence is: technical accuracy/security/active policy → ticket thread and ITSM notes → team rules → operator-local preference → agent default.

### Final checks

`tickets/<번호>.md` 의 `## 발송 전 점검` 을 채운 뒤 아래를 함께 본다.

- Every definitive statement is supported by a `[확인]` item that carries a source.
- 위 10번의 "전달드렸습니다" 줄을 함께 본다.

## 쓰기 전에

* `[대괄호]` 부분은 실제 내용으로 바꾸고, 해당하지 않는 항목과 안내용 주석은 삭제한다.
* 00은 접수 확인용 1차 답변이다. 접수 안내만으로 문의를 해결 처리하지 않으며, 이후 확인된 답변이나 진행 상황을 안내한다.
* 완료 시점이나 진행 안내 일정은 확인 가능한 경우에만 제시한다. 기본 문구는 확인 결과와 진행 상황 안내로 구성하고, 날짜·시간 필드는 선택 사항으로 둔다. 고객과 일정을 합의한 경우에는 해당 시점에 진행 상황을 알린다.
* 고객에게 날짜를 안내하지 않더라도 내부 재확인 주체·일정을 기록한다. 장기 확인 건은 내부 기준에 따라 진행 상황을 공유하며, 고객과 합의한 일정을 지키기 어려워지면 변경 내용을 알린다.
* 고객이 접근 가능한 정보와 확인된 근거를 사용한다. 내부 운영·정산 로직 등 공개 범위가 불명확한 정보는 담당 부서에 안내 가능 여부를 확인한다.

# 접수

## 00. 문의 접수 안내 (1차 답변)

**언제** — 문의가 접수되어 내용 검토를 시작할 때. 이미 자동 접수 안내가 발송된 경우에는 중복 안내 필요 여부를 확인한다. 확인 작업을 시작한 이후 중간 안내는 02를 사용한다.

```
안녕하세요.
MSP 회사 [이름] 프로입니다.

문의주신 [문의 요지]가 접수되었습니다.
문의 내용을 검토한 후 안내드리겠습니다.
추가 정보가 필요한 경우 별도로 요청드리겠습니다.

감사합니다.
```

# 답변

## 01. 확인 질문 답변

**언제** — 고객이 "\~인가요?", "\~맞나요?"로 물었을 때. 결론을 먼저 안내하되 예/아니오에 한정하지 않는다. 조건에 따라 달라지면 적용 조건을 설명하고, 추가 확인이 필요하면 02를 사용한다.

```
안녕하세요.
MSP 회사 [이름] 프로입니다.

문의주신 [질문 요지]에 대해 답변드립니다.

▪ 결론 : [확인된 결론 — 예/아니오 또는 조건을 포함한 설명]
▪ 근거 : [고객 계정에서 확인한 값 또는 AWS 문서의 해당 항목]
▪ 확인 방법 : [고객이 확인 가능한 명령어 / 화면 경로 / 문서 항목]
  확인 결과 : [확인된 값 또는 판단 기준]

[유효 조건이나 예외가 있으면 여기에]

추가 문의 사항이 있으시면 회신 부탁드립니다.
감사합니다.
```

## 02. 즉시 확답이 어려울 때

**언제** — 접수 후 환경 확인, 로그 분석, 유관 부서 또는 벤더 확인이 진행 중일 때. 확인된 내용이 있으면 먼저 안내하고, 확인 자체가 어려우면 그 이유와 확인 가능한 범위를 설명한다. 구체적인 날짜나 다음 일정을 매번 약속할 필요는 없으며, 실제 안내가 가능한 경우에만 추가한다.

```
안녕하세요.
MSP 회사 [이름] 프로입니다.

문의주신 [내용]을 확인하고 있습니다.

▪ 현재 확인된 사항 : [확인된 내용 — 없는 경우 이 항목 삭제]
▪ 추가 확인 사항 : [확인이 필요한 항목]
▪ 진행 중인 작업 : [로그 분석 / 환경 확인 / 유관 부서 또는 AWS 문의 등]

확인이 완료되면 검토 결과를 안내드리겠습니다.
확인이 장기화되는 경우 진행 상황을 공유드리겠습니다.

감사합니다.
```

고객과 진행 안내 일정을 합의한 경우에만 아래 문구를 추가한다.

```
[합의한 안내 시점]에 진행 상황을 공유드리겠습니다.
```

## 04. 비용 답변

**언제** — 과금 방식 설명은 04-A, 비용 증감 원인 설명은 04-B를 사용한다. 공식 요금 기준에 따른 참고 금액과 과금 설명은 아래 판단 기준에 따라 안내하고, 계약 견적·제안은 05로 이관한다.


:::warning
**주의** — 최신 요금 기준과 고객 환경에서 확인 가능한 자료를 근거로 답한다. 추가 확인이 필요하면 **02**로 진행 상황을 안내한다. 내부 운영·정산 로직은 공개 가능 여부를 확인한다. **참고 금액과 계약 견적을 구분하며, 역할 판단 기준은 05를 참조한다.**

:::

### 04-A. 과금 방식 안내

서비스별로 비용 항목을 묶어 설명한다. 고정 성격 비용은 명시한 계약·구성·기간 조건에서 사용량과 별개로 발생하는 비용이며, 사용량에 따른 비용은 사용량·가동 시간 등에 따라 달라지는 비용이다. 고정 성격 비용도 계약·구성 변경에 따라 달라질 수 있으므로 조건을 명시한다. RI/SP는 계약·약정 조건을 확인한 뒤 설명하며 일괄적으로 고정비로 분류하지 않는다. 오차 범위를 근거 없이 수치로 제시하지 않는다.

```
안녕하세요.
MSP 회사 [이름] 프로입니다.

문의주신 [서비스]의 과금 방식을 안내드립니다.

▪ [서비스명]
  - [비용 항목] : [고정 성격 / 사용량에 따라 변동 / 약정 조건 적용 등]
    과금 기준 : [단가 및 과금 단위 / 계약상 비용]
    적용 조건 : [구성 / 기간 / 사용량 / 약정 등]
  - [추가 비용 항목]
    과금 기준 : [해당 기준]
    적용 조건 : [해당 조건]

▪ 근거 : [요금 페이지 또는 안내 가능한 계약 기준 및 해당 항목]
▪ 실제 청구와 차이가 발생할 수 있는 사유 : [이번 안내에 해당하는 사유]

감사합니다.
```

### 04-B. 비용 증감 원인 안내

비교 기간과 확인된 데이터를 명시한다. 원인을 확정하기 어려우면 확인된 변화와 추가 확인 사항을 구분하고 02로 진행 상황을 안내한다.

```
안녕하세요.
MSP 회사 [이름] 프로입니다.

문의주신 [서비스명 / O월 비용 증감 건]에 대해 안내드립니다.

▪ 비교 기준 : [비교 기간 / 통화 / 데이터 집계 기준]
▪ 확인된 비용 변화 : [이전 기간 대비 증감 내용]
▪ 주요 원인 : [확인된 원인 또는 현재 확인 중인 항목]
▪ 상세 확인 내역
  - 서비스 및 대상 리소스 : [서비스명 / 리소스 식별자]
  - 확인 데이터 : [사용량·단가·구성 변화와 발생 기간]
  - 비용에 미친 영향 : [자료로 확인된 영향]
▪ 직접 확인 방법 : [고객이 접근 가능한 빌링 포털 또는 화면 경로]
  확인 기준 : [기간 / 서비스 필터 등]
▪ 안내 사항 : [집계 시점 및 실제 청구와 차이가 발생할 수 있는 사유]

감사합니다.
```

## 06. 지원 범위 밖 + 대안

**언제** — 지원 범위에 포함되지 않는 요청. 가능한 경우 인접 지원 범위와 대안을 제시한다. 고객 요건에 맞지 않는 대안을 강제로 제시하지 않는다. 아키텍처 방향 안내와 실제 구성·구축 수행을 구분한다. AWS 외 서비스나 익숙하지 않은 서비스의 비교·권장은 검증 가능한 지식과 자료가 있는 경우에만 안내한다.

```
안녕하세요.
MSP 회사 [이름] 프로입니다.

문의주신 [대상]은 MSP 회사 지원 범위에 포함되지 않아
구성 및 가이드를 직접 제공드리기 어려운 점 양해 부탁드립니다.

다만 아래 범위는 저희가 진행해 드릴 수 있습니다.
▪ 지원 가능한 행위 : [범위 / 안내만 제공하는지 실제 작업까지 수행하는지]
▪ 지원하지 않는 행위 : [직접 구축 / 타 서비스 검증 등 제외 범위]
▪ 수행 주체 : [MSP 회사 / 고객 / 외부 업체의 역할]
▪ 대안 안내 : [확인 가능한 대안과 제공 범위 — 해당하는 경우]

[검증 가능한 지식·자료가 있는 경우에만 비교 또는 권장 이유와 제한 사항 작성]

희망하시는 방향을 말씀 주시면 위 지원 범위와 수행 주체를 기준으로 다음 조치를 안내드리겠습니다.
감사합니다.
```

**적용 가능한 대안이 없는 경우** — 위의 지원 가능 범위·대안·진행 요청 문구 대신 아래 내용을 사용한다. 안내할 수 있는 경로가 없다면 그 사실을 설명하며 지원 가능성을 약속하지 않는다.

```
현재 확인한 범위에서는 요청하신 [필수 요건]을 충족하는 대안을 안내드리기 어렵습니다.
[확인 가능한 공식 지원 경로 / 담당 부서 / 추가 검토에 필요한 사항]
```

## 08. 앞선 답변 정정

**언제** — 내 답변이나 동료 답변이 틀렸을 때. 숨기지 않고 명시적으로 바로잡는다 — 정정을 드러내는 편이 신뢰를 만든다.

```
안녕하세요.
MSP 회사 [이름] 프로입니다.

앞서 안내드린 [내용]에 대해 보완하여 말씀드립니다.

▪ 정정 : 앞서 [기존 안내] 로 안내드렸으나,
  정확히는 [정정된 내용] 입니다.
▪ 사유 : [왜 달라지는지 — 실제 동작 원리나 근거]
▪ 확인 방법 : [명령어 또는 문서의 해당 항목]
  실행 결과 : [결과]

혼선을 드려 죄송합니다.
[정정에 따라 고객이 다시 판단해야 할 사항이 있으면 여기에]

감사합니다.
```

# 요청 · 이관

## 03. 구조화 정보 요청

**언제** — 아키텍처나 예상 규모 검토에 정보가 필요할 때. 필요한 항목만 선택하여 요청한다. 고객이 수치를 모르면 예상 범위나 현재 운영 자료를 받고 가정을 기록한다. 견적 관련 역할 판단은 05를 참조한다.

**요청 예시** — 신규 웹 서비스의 초기 규모 검토에는 예상 사용자 수·요청량·가용성 요건을, 마이그레이션 검토에는 현재 구성·사용량·전환 제약을, 성능 문의에는 발생 시간·대상 리소스·관련 로그를 요청한다. 과금 방식만 묻는 문의에 모든 규모 정보를 요청하지 않는다.

```
문의주신 내용을 검토하기 위해 아래 정보를 확인 부탁드립니다.

A) 요건
   1) [요건 질문]
   2) [적용 범위 — 전체인지 특정 서비스인지]
   3) [예외 대상이 있는지]

B) 환경 정보
   1) [버전 / 구성]
   2) [리소스 식별자]

C) 예상 규모 검토에 필요한 정보
   ※ 파악하기 어려운 항목은 예상 범위 또는 현재 운영 자료로 전달 부탁드립니다.
   1) 피크 시 초당 요청 수(RPS)
   2) 월 총 요청 건수
   3) 월 데이터 전송량(GB)

D) 추가 확인
   1) [질문]

제공해 주신 정보와 [검토 가정 및 기준]을 바탕으로 검토하여 안내드리겠습니다.
감사합니다.
```

신규 구성이나 마이그레이션은 초기 가정과 검토 조건을 기록한다. 안정화 이후 실제 사용량과 모니터링 결과에 따라 구성 조정이 필요할 수 있음을 해당 상황에서 안내한다.

## 05. 견적 요청 이관 (Sales)

**언제** — 계약 금액, 고객별 할인·약정, 정식 견적·제안 등 Sales의 확인이 필요한 문의. 모든 비용 문의를 일괄 이관하지 않는다.

**역할 판단 기준(검토안)**

* 기술 담당자: 공식 문서의 과금 단위·온디맨드 요금·공개된 RI 할인 조건, 명시한 사용량과 가정에 따른 참고 금액을 설명할 수 있다. 참고 금액은 확정 견적이나 실제 청구 금액으로 안내하지 않는다.
* 기술적 비용 분석: 사용량·리소스 변화 등 확인 가능한 사실을 정리한다. CUR 등 자료는 접근 권한과 고객 공개 가능 범위를 확인한 뒤 사용하며, 청구·정산 판단이 필요하면 해당 담당 부서에 확인한다.
* Sales 등 담당 부서: 계약 견적, 고객별 할인·약정 조건, 상업적 제안과 계약상 과금 기준을 확인한다. 일반 과금 문의도 공개 요금 설명인지 고객별 계약·정산 문의인지 구분하여 처리한다.
* 구분이 어려운 경우: 고객을 바로 이관하기 전에 내부적으로 확인 주체를 정한다. 이 기준은 의견이 엇갈린 부분에 대한 초안이며 내부 업무 분장과 대조하여 확정한다.


:::warning
**경계** — 사양 적합성 등 지원 가능한 기술 검토는 계속 진행한다. 전달 완료 여부를 확인한 뒤 고객에게 안내하고, 내부 확인 주체·재확인 일정을 기록한다. 티켓 상태는 대기 사유와 운영 기준에 맞게 설정한다.

:::

```
안녕하세요.
MSP 회사 [이름] 프로입니다.

요청주신 [변경 내용] 견적은 Sales 부서 소관으로,
Sales 부서에 전달드렸습니다.

▪ 전달한 내용
  - 현재 사양 : [현재 구성]
  - 변경 희망 : [제안 사양]
  - 기타 조건 : [사용 시간 / 스토리지 / 계약 조건 등]
▪ 진행 상황은 제가 확인하여 안내드리겠습니다.

사양 적합성 검토나 과금 구조에 대한 문의는
제가 계속 지원드리겠습니다.

확인 결과의 회신 일정이 확인되면 안내드리겠습니다.
확인이 장기화되는 경우 진행 상황을 공유드리겠습니다.
감사합니다.
```

## 07. 타 부서 이관 및 벤더 확인

**언제** — Sales·FinOps 등으로 넘길 때. 전달 사실과 후속 안내 방식을 알린다. 진행 안내 일정은 확인 가능한 경우에만 추가한다. 담당자명은 필요한 경우에만 안내하고, 내부 확인 주체는 기록한다.


:::warning
**주의** — 이관으로 끝내지 않는다. 내부 재확인 일정에 진행을 확인하고, 고객과 안내 시점을 합의한 경우 해당 시점에 안내한다. 일정이 미정인 경우에도 장기 확인 건의 진행 상황을 공유한다. 완료 예정은 해당 부서에서 확인된 경우에만 안내한다. 티켓 상태는 대기 사유와 운영 기준에 맞게 설정한다.

:::

```
안녕하세요.
MSP 회사 [이름] 프로입니다.

문의주신 [내용]은 [부서] 소관으로,
[부서]에 관련 내용을 전달드렸습니다.

▪ 진행 상황은 제가 확인하여 안내드리겠습니다.

확인 결과의 회신 일정이 확인되면 안내드리겠습니다.
확인이 장기화되는 경우 진행 상황을 공유드리겠습니다.
감사합니다.
```

# 기록

## 09. 작업 완료 보고

**언제** — 요청 작업을 마쳤을 때. 대상, 적용 내용, 시각과 확인 결과를 남긴다. 상세 리소스 목록·접속 정보·변경 내역은 접근 가능한 첨부 파일로 전달할 수 있으며, 티켓 본문에는 작업 요약·핵심 결과·첨부 파일명 또는 저장 위치를 남긴다. 첨부를 사용하는 항목은 본문에 중복 작성하지 않아도 된다.


:::warning
**주의** — 비밀번호 · 액세스 키 · 토큰은 본문에 쓰지 않는다. 압축 비밀번호는 건별 생성하고, 압축 파일과 비밀번호를 서로 분리된 승인된 전달 경로로 보낸다. 같은 메일이나 티켓에 파일과 비밀번호를 함께 기재하지 않는다.

:::

```
안녕하세요.
MSP 회사 [이름] 프로입니다.

요청주신 [작업] 완료하여 회신드립니다.

▪ 대상 : [리소스 ID / 이름]
▪ 적용 내용 : [변경 전] → [변경 후]
▪ 적용 시각 : [O월 O일 O시]
▪ 상세 내역 : [본문 내역 / 첨부 파일명 또는 접근 가능한 저장 위치]
▪ 접속 정보 : [공개 가능한 정보 / 첨부 참조 / 해당 없으면 삭제]
  ※ 키페어 및 비밀번호는 별도 안내드리겠습니다
▪ 확인 결과 : [수행한 확인 및 결과]
▪ 확인 방법 : [고객이 정상 여부를 확인할 방법]

[후속 필요 작업 또는 주의사항]

감사합니다.
```

**언제** — 문의가 마무리됐을 때. **실질 답변 또는 작업 완료 안내와 함께 사용할 수도 있다.**


:::warning
**주의** — 누르기 전에 내가 이 고객에게 **실질 답변을 보냈는지** 확인한다. 접수 안내와 이 문구만으로 티켓을 닫지 않는다. 장애 관련 알람은 복구 확인 결과를 기록하고, 원인이 미확인인 경우 그 상태와 후속 확인 필요 여부를 남긴다. 그 외 알람도 성격에 맞는 확인 결과를 기록한다. 처리 결과가 앞선 답변에 있으면 종료 안내에서 반복할 필요는 없다. 진행 중인 확인·이관 사항이 없는지 확인하며, 세부 기준은 표준 및 운영 정책과 대조한다.

:::

```
안녕하세요.
MSP 회사 [이름] 프로입니다.

문의주신 내용에 대한 안내가 마무리되어
본 티켓을 해결 처리하고자 합니다.

추가 확인이 필요한 사항이 있으시면 회신 부탁드립니다.
감사합니다.
```

### 작업 완료와 함께 해결 처리하는 경우

AMI 최신화 등 요청 작업이 완료되고 정상 확인까지 끝났으며, 추가 확인·이관·고객 승인 사항이 남지 않은 경우 09와 종료 안내를 한 번에 보낼 수 있다. 고객 확인이 필수인 건에는 적용하지 않는다.

```
[09의 작업 완료 내용 및 확인 결과]

요청하신 작업이 완료되고 정상 확인되어 본 티켓을 해결 처리하겠습니다.
추가 문의 사항이 있으시면 회신 부탁드립니다.
```

### 고객 회신이 없어 해결 처리 전 안내하는 경우

실질 답변을 제공한 건에 사용한다. 미완료 요청이나 고객 확인이 필수인 작업은 무응답만을 이유로 완료한 것으로 간주하지 않는다. 대기 기간과 처리일은 운영 기준에 따라 정한다.

```
안녕하세요.
MSP 회사 [이름] 프로입니다.

앞서 안내드린 내용과 관련하여 추가 문의 사항이 있으신지 확인드립니다.
[O월 O일]까지 추가 문의가 없으시면 본 티켓을 해결 처리할 예정입니다.
추가 확인이 필요하시면 회신 부탁드립니다.

감사합니다.
```

재문의 방법은 실제 티켓 동작에 맞게 추가한다. 해결 상태에서 회신으로 재개되는 경우와 자동 종료 이후 새 문의가 필요한 경우를 구분한다.
