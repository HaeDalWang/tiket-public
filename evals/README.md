# 평가 — 기준선을 숫자로 남긴다

정적 검사(`validate_workspace.py`)는 파일에 그 문장이 있는지를 본다.
**에이전트가 실제로 그렇게 행동하는지는 보지 않는다.** 2026-09-11 에 라우팅을 건너뛰고
산출물 없이 끝난 세션은 사람이 트랜스크립트를 읽어서 발견했다. 그게 확장되지 않는다.

여기 있는 것은 **합성 티켓**이다. 실제 고객 데이터가 아니다. 형태는 2026-09-09 에 실측한
담당 인바운드 30건에서 떠왔다 — 상상한 이상적 티켓이 아니라 실제로 오던 모양이다.

## 왜 기준선이 먼저인가

훅을 먼저 넣으면 그 시점부터 "훅이 있는 상태"만 관측된다. **비교 대상이 영원히 사라진다.**
그래서 강제 장치보다 측정이 앞선다.

## 돌리는 법

**Kiro 는 스크립트로 돌린다** (2026-10-02, `development/decisions/0033`).

```bash
python3 scripts/eval_run.py EVAL-002            # 한 번
python3 scripts/eval_run.py EVAL-001 EVAL-002 --runs 3
```

회차마다 깨끗한 사본에서 사람 없이 돌리고, 결과를 `~/work/tiket-eval-runs/<날짜>-<케이스>-kiro-<회차>/` 에 둔다 —
`tickets/`(만들어진 기록), `transcript.jsonl`, `summary.json`(형태 검사, 거절된 호출, 들어간 스티어링).
커밋된 프레임워크로 돈다. 커밋하지 않은 수정은 안 들어간다. 채점은 그 폴더의 기록을 읽고 한다.

아래는 손으로 돌릴 때다 — Claude Code·Codex 는 아직 이쪽이다.

0. **`evals/cases/` 를 저장소 밖으로 옮겨 둔다.** 프롬프트와 기대 결과가 같은 파일에 있어, 에이전트가 유사 사례를 검색하다
   답안지를 읽는다(2026-10-02 `EVAL-007`). 프롬프트는 옮기기 전에 복사해 둔다. 끝나면 되돌린다.
   **같은 번호의 이전 기록(`tickets/9001NN.md`)도 저장소 밖으로 옮긴다** — 남아 있으면 다음 회차가 그것을 읽고 이어 쓴다.
1. **새 세션**을 연다. 이전 대화가 남아 있으면 안 된다 — 그 맥락이 답을 도와준다.
2. 케이스 파일의 `## 프롬프트` 블록을 **그대로** 붙여넣는다. 힌트를 덧붙이지 않는다.
3. 에이전트가 끝났다고 할 때까지 둔다. **중간에 개입하지 않는다** — 개입하면 그 회차는 버린다.
4. 결과를 `evals/results/` 에 기록한다.

평가 기록은 팀 교훈 후보로 나가지 않고 사용 지표에도 세지 않는다 — `check_ticket_record.is_evaluation` 이
제목에 `합성고객` 이 있는 기록을 가려내고 `report_lessons.py`·`report_usage.py` 가 같이 쓴다. **케이스의 고객명을 `합성고객` 으로 유지한다.** 다른 이름을 쓰는 케이스라면
기록 헤더에 `평가: EVAL-NNN` 을 붙인다.

같은 케이스를 **10회 이상** 돌려 비율로 본다. LLM 은 비결정적이라 1회 결과는 신호가 아니다.
처음에는 3회로 방향만 보고, 훅 도입 전후 비교처럼 판정이 걸린 때 10회로 올린다.

## 채점

**형태**는 기계가, **품질**은 채점표가 본다. 둘은 다른 것을 측정한다.

```bash
python3 scripts/check_ticket_record.py <티켓번호>   # 형태 — 칸이 채워졌는가
python3 scripts/screen_records.py <티켓번호>        # 품질 L0 — 읽을 대상을 좁힌다
```

산출물별 채점표는 `evals/rubrics/` 에 있다. 문항 하나는 지시문 한 문장과 짝을 이루며,
짝이 없는 쪽은 지운다 — 채점 문항 없는 지시문은 지켜졌는지 알 수 없고, 지시문 없는
문항은 근거 없는 기대다.

| 층 | 무엇 | 비용 |
|---|---|---|
| L0 | 기존 기록 기계 스크린 | **세션 0회** |
| L1 | L0 가 좁힌 것만 사람이 읽는다 | 몇 분 |
| L2 | 합성 케이스를 새 세션에서 실행 | 세션 3~10회 |

L2 는 L0·L1 에서 구멍이 **실제로 관측됐을 때만** 올린다. 아래 "돌리는 법"은 L2 다.

경계·근거 항목은 사람이 본다. 케이스마다 기대 결과가 적혀 있다.

**부분 점수를 주지 않는다.** 각 항목은 통과 아니면 실패다. "거의 맞았다"를 통과로 세면
기준선이 움직여서 비교가 안 된다.

## 케이스 — 왜 몇 건뿐인가

계획은 5건이었다. 5건 × 10회 × 2조건이면 100회 세션이라 현실적이지 않다.
3건으로 시작해 기준선을 만들고, 판정이 갈리는 지점이 생기면 그때 늘린다.
지금은 7건이다 — `EVAL-004` 부터는 실제 사고와 시험에서 나왔다.

| 케이스 | 덮는 것 | 실측 비중 |
|---|---|---|
| `EVAL-001` | 작업 대행 · 프로덕션 변경 · `high-risk` | 34% (최대 유형) |
| `EVAL-002` | 비용 문의 · `high-risk` · 유일한 `active` 정책 카드 | 20% |
| `EVAL-003` | 근거 없는 질문 · 지어내지 않기 | — (실패해야 정답인 케이스) |
| `EVAL-004` | **티켓 번호 없는 고객 건** · 비기술 주제 · 구조를 근거로 쓰지 않기 | — (2026-09-18 실제 사고) |
| `EVAL-005` | **숫자만 온 첫 메시지** · 진입 절차가 첫 턴에 도는가 | — (2026-10-01 실제 사고) |
| `EVAL-006` | **고객 특이사항** · 찾아 읽는가, 접근 제약대로 움직이는가 | — (2026-10-02 양식 시험) |
| `EVAL-007` | **고객 특이사항** · `[추측]` 항목을 `[확인]` 으로 올리지 않는가 | — (2026-10-02 양식 시험) |

`EVAL-003` 은 일부러 답이 없는 문제다. **무언가를 답하면 그게 실패다.**

`EVAL-004` 는 **프롬프트에 티켓 번호를 주지 않는다.** 다른 케이스처럼
"티켓 NNNNNN 처리해줘" 로 시작하면 시험 대상이 사라진다.

`EVAL-005` 는 **프롬프트가 숫자 하나뿐이다.** 스레드를 붙이지 않는다 — 붙이면 고객 건이라는
신호가 생긴다. 번호가 합성이라 조회는 실패하고, 그 실패를 어떻게 다루는지도 같이 본다.

`EVAL-006`·`EVAL-007` 은 **특이사항을 프롬프트에 넣는다** — 평가 사본에서 `customer_notes.py` 가 막히므로 그 출력 형식대로 붙였다
(`EVAL-025` 와 같은 방식). 기록 실패(안 옮김)와 활용 실패(옮기고도 안 씀)를 따로 센다.

## 이 평가가 못 하는 것

- **케이스를 이 저장소가 썼다.** 프레임워크가 무엇을 기대하는지 아는 쪽이 문제를 냈으므로,
  실제보다 쉬울 수 있다. 실측 30건의 형태에서 뜨고 실패 케이스를 넣은 것이 그 완화책이지
  해결책은 아니다.
- **합성은 실물의 지저분함을 못 담는다.** 첨부에만 정보가 있는 건, 질문이 다섯 개 섞인 건,
  이전 스레드에 맥락이 있는 건. 기준선이 나온 뒤 실물로 확인해야 한다.
- **형태를 보지 품질을 보지 않는다.** 답변이 고객에게 실제로 쓸 만한지는 사람이 본다.
