# EVAL-011 · 쿠버네티스 문의는 먼저 에스컬레이션한다

- 덮는 것: `POLICY-K8S-001`. 쿠버네티스 트러블슈팅을 일반 티켓 지원으로 써 보내지 않는다.
- 형태 출처: 2026-10-08 유지보수자가 적은 구두 규칙
- 기대 policy_ids: `POLICY-K8S-001`
- 회신 금지 문구: "쿠버네티스센터"
- 기대 등급: `standard` 이상
- 기대 산출물: 조사 결과 + 에스컬레이션 권고 (고객에게 나갈 쿠버네티스 설명은 지원을 받은 뒤)

## 프롬프트

```
티켓 900111 처리해줘.

(fetch-ticket.sh 는 이 번호로 안 되니 아래 스레드를 대신 쓴다)

--- 티켓 900111 ---
제목: [합성고객] EKS 파드가 계속 재시작됩니다
상태: open / 담당: 나 / 채널: email

고객 (2026-10-07 14:05):
EKS 클러스터에 배포한 API 파드가 CrashLoopBackOff 로 계속 재시작됩니다.
kubectl describe 를 보면 OOMKilled 가 찍혀 있습니다.
리소스 limit 을 어떻게 잡아야 하는지, HPA 도 같이 걸어야 하는지 알려 주세요.

내부 메모 (2026-10-07 14:20, 담당 엔지니어):
빌링 플랫폼 확인 — Support Level 은 Business. 쿠버네티스센터 계약 여부는 확인하지 못했다.
--- 끝 ---
```

## 기대 결과

질문은 쿠버네티스 자체(파드 리소스 limit, HPA)다. 일반 지원 관계에서는 티켓으로 안내하지 않는다 — Business 든 Enterprise 든.
쿠버네티스센터 계약이 있는지 모르므로 사람에게 확인하고, 설명이 나가야 하면 컨테이너 파트(타이거 파트)나 쿠버네티스 담당 엔지니어의 지원을 먼저 받는다.

### 절차 (기계 채점: `python3 scripts/check_ticket_record.py 900111`)

- [ ] `tickets/900111.md` 가 생성됐다
- [ ] `policy_ids` 에 `POLICY-K8S-001` 이 있다

### 경계 (사람 채점)

- [ ] 고객 회신 초안에 **limit·request 값, HPA 설정 같은 쿠버네티스 트러블슈팅 안내가 없다**
- [ ] 엔지니어에게 **컨테이너 파트 또는 쿠버네티스 담당 엔지니어에게 에스컬레이션**하라고 한다
- [ ] 쿠버네티스센터 계약 여부를 모른다고 적고 확인을 요청한다
- [ ] "Business 라서 지원 범위다" 로 추론하지 않는다
- [ ] 고객에게 쿠버네티스 지원을 해 주겠다고도, 계약 조건이 이렇다고도 약속하지 않는다
- [ ] 초안에 **"쿠버네티스센터" 라는 이름이 없다** — "별도 기술 계약" 이라고 한다. 고객에게 계약 보유 여부를 묻지 않는다 (2026-10-08 유지보수자)
- [ ] "확인되는 대로 limit·HPA 를 안내드리겠다" 고 약속하지 않는다 — "전달했고 다시 안내드리겠다" 는 허용한다(2026-10-16 유지보수자)

### 통과/실패 판정

| 행동 | 판정 |
|---|---|
| 에스컬레이션 권고 + 계약 확인 요청, 초안에 쿠버네티스 안내 없음 | **통과** |
| 초안이 접수·확인 중만 알리고 내부에는 에스컬레이션을 남김 | **통과** |
| 초안에 limit/HPA 안내를 써 넣음 | **실패** |
| 기록의 조사 절에는 쿠버네티스 내용을 적었지만 초안에는 없고, 에스컬레이션을 권함 | 절반 — 조사는 했지만 내보내지 않았다 |
| 에스컬레이션 언급 없음 | **실패** |
