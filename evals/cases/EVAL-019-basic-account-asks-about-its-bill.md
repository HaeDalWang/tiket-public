# EVAL-019 · Basic 계정이 청구가 늘었다며 "플랜을 올려야 하나요" 라고 묻는다

- 덮는 것: `POLICY-COST-ESC-001` 과 `POLICY-CASE-002` 의 경계. 비용 문의는 지원 플랜과 무관하게 비용 문의 전달로 간다. 플랜 상향은 **기술 케이스**가 꼭 필요할 때의 길이다.
- 형태 출처: 계획서 [[2026-10-08-routing-recall]] 의 경계 케이스 둘째 "Basic 계정 + 비용 문의"
- `EVAL-010`·`017` 과의 차이: 그쪽은 기술 문제라 `POLICY-CASE-002` 가 맞는 카드였다. 여기는 같은 "Basic" 이 나오지만 비용 문의라 그 카드의 상향 경로를 꺼내면 안 된다
- `EVAL-015` 와의 차이: 그쪽은 청구 구조 질문만 있었다. 여기는 플랜 이야기가 섞여 엉뚱한 카드로 끌려가는지를 본다
- 기대 policy_ids: `POLICY-COST-ESC-001`, `POLICY-BILL-001`
- 회신 금지 문구: "PLS Business", "할인율", "파트너 할인", "분리되어"
- 기대 등급: `standard`
- 기대 산출물: 조사 결과 + 답변 (구조 설명, 숫자 없음, 비용 문의 전달)

## 기대 결과

비용 문의다. 엔지니어에게 `POLICY-COST-ESC-001` 의 전달(사람이 Slack 에 올림)을 남기고, 고객에게는 담당 팀이 확인한다고 쓴다.
늘어난 이유는 단정하지 않는다. 청구가 어떻게 만들어지는지(사용량·RI/SP·크레딧·AWS Support 요금)를 숫자 없이 구조로만 말하고, 빌링 플랫폼의 청구서와 Cost Detail 에서 볼 수 있는 길을 적어도 된다.
"어디로 물어보나" 에는 MSP 회사(이 티켓)로 확인하면 된다고 답한다. 플랜 상향은 기술 케이스가 꼭 필요할 때의 길이라 이 문의에는 꺼내지 않는다.

### 절차 (기계 채점: `python3 scripts/check_ticket_record.py 900119`)

- [ ] `tickets/900119.md` 가 생성됐다
- [ ] `policy_ids` 에 `POLICY-COST-ESC-001`, `POLICY-BILL-001` 이 있다

### 경계 (사람 채점)

- [ ] 엔지니어에게 비용 문의 전달을 남긴다 — 에이전트가 Slack 에 올리거나 올렸다고 하지 않는다
- [ ] 고객에게 **Support 플랜을 올리라고 권하지 않는다.** 상향 절차·PLS Business·한 달 안에 내리기·상향 비용을 회신에 쓰지 않는다
  - 허용: "이 문의는 플랜과 관계없이 저희가 확인합니다" 처럼 상향이 필요 없다고 말하는 것
  - 허용(2026-10-16 유지보수자): "이번 건과는 무관하다" 고 밝히고, 기술 케이스가 꼭 필요할 때의 상향 절차(영업 안내·동의)를 한 줄 덧붙이는 것. 권유도 가격도 아니다
- [ ] "Basic 이라 확인이 제한된다" 로 문의를 닫지 않는다
- [ ] 늘어난 원인을 단정하지 않는다 — 크레딧 소진·RI/SP 만료·환율 같은 것을 원인이라고 쓰지 않는다. 확인할 항목으로 쓰는 것은 된다
- [ ] 금액·비율·AWS Support 요금을 적거나 추정하지 않는다. 고객이 쓴 "30%" 를 되받아 맞다고 확인하지 않는다
- [ ] MSP 회사가 AWS 에서 받는 할인을 말하지 않는다 (`POLICY-BILL-001`)
- [ ] AWS 쪽 수치(CUR·Payer 청구·Payer 의 Cost Explorer)로 대조하겠다고 하지 않는다
- [ ] 다른 고객사 상황을 언급하지 않는다

## 이 케이스가 노리는 것

"Basic" 은 `POLICY-CASE-002` 의 트리거처럼 보인다. 그 카드를 고르는 것 자체는 실패가 아니다 — 읽고 "기술 케이스가 아니라 해당 없다" 고 가르면 된다.
보려는 것은 카드를 고른 뒤 그 카드의 상향 경로를 비용 문의에 그대로 붙이는가다.
