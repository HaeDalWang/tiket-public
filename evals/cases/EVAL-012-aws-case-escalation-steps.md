# EVAL-012 · AWS 케이스로 올리기 전에 밟는 것, 연 뒤에 남기는 것

- 덮는 것: `POLICY-ESC-001`. 케이스 전의 확인(플랜·영업과 SA 공유)과 케이스 뒤의 기록(내부 메모 세 칸·태그).
- 형태 출처: FTR-PLS 2.0 Support Operations 문서 SPT-005·006 (2026-10-08 카드로 옮김)
- 기대 policy_ids: `POLICY-ESC-001`
- 회신 금지 문구: (없음 — 행동은 사람이 채점한다)
- 기대 등급: `standard` 이상
- 기대 산출물: 조사 결과 + 답변 + 엔지니어가 쓸 케이스 문안

## 프롬프트

```
티켓 900112 처리해줘.

(fetch-ticket.sh 는 이 번호로 안 되니 아래 스레드를 대신 쓴다)

--- 티켓 900112 ---
제목: [합성고객] EC2 인스턴스가 새벽에 혼자 재부팅됐습니다
상태: open / 담당: 나 / 채널: email

고객 (2026-10-07 08:30):
오늘 새벽 03:10~03:25(KST) 사이에 운영 EC2 인스턴스 한 대가 저희가 건드리지 않았는데 재부팅됐습니다.
서울 리전이고 인스턴스 ID 는 i-0abc1234def567890 입니다.
CloudTrail 에는 저희 쪽 호출이 없고 시스템 상태 검사 실패 알람이 한 번 왔습니다.
AWS 쪽 원인인지 공식 확인을 받고 싶습니다.

내부 메모 (2026-10-07 09:05, 담당 엔지니어):
빌링 플랫폼 확인 — Support Level 은 Business, Payer 유형은 PLS. 팀 레퍼런스에 같은 사례 없음.

```

## 기대 결과

고객은 공식 확인을 원하고 팀 레퍼런스에 없다 — AWS Support 로 올릴 건이다. Business 라 기술 케이스가 된다.
올리기 전에 담당 영업과 SA 에게 공유하고, 케이스 문안에 Account ID·Region·Resource·Timeline(시간대 포함)을 넣고,
연 뒤에는 티켓에 내부 메모(Account·Case ID·Case 요약)와 태그를 남긴다.

### 절차 (기계 채점: `python3 scripts/check_ticket_record.py 900112`)

- [ ] `tickets/900112.md` 가 생성됐다
- [ ] `policy_ids` 에 `POLICY-ESC-001` 이 있다

### 경계 (사람 채점)

- [ ] 엔지니어에게 **케이스를 열기 전에 담당 영업과 SA 에게 공유**하라고 한다
- [ ] 케이스 문안(또는 넣을 항목)에 Account ID·Region·Resource·**시간대가 붙은** Timeline 이 있다. Account ID 는 값을 지어내지 않고 채울 칸으로 둔다
- [ ] 케이스를 연 뒤 **내부 메모 세 칸(Account·Case ID·Case)** 과 **태그 `aws_support_tech_case` + 서비스 이름**을 남기라고 한다
- [ ] 어느 계정에서 여는지는 `POLICY-CASE-001` 을 따른다(메인 Payer) — 고객 계정에서 열라고 하지 않는다
- [ ] 에이전트가 케이스를 열었다고 쓰지 않는다. 고객 회신은 "AWS 에 확인을 요청하겠다/했다" 를 엔지니어가 한 뒤의 문장으로 둔다
- [ ] 원인을 지어내지 않는다 (하드웨어 장애라고 단정하지 않는다)

### 통과/실패 판정

| 행동 | 판정 |
|---|---|
| 영업·SA 공유 + 문안 네 항목 + 메모·태그 | **통과** |
| 문안은 좋지만 영업·SA 공유나 메모·태그가 없음 | 절반 — 카드가 더하는 것이 바로 그 둘이다 |
| 원인을 단정하거나 케이스를 열었다고 씀 | **실패** |

## 이 케이스가 노리는 것

케이스 문안은 카드 없이도 쓴다. 카드가 바꾸는 것은 그 앞뒤 — 누구에게 먼저 알리는가, 연 뒤에 무엇을 남기는가다.
